# ServGo — единый диспетчер и выполнение поручений ИИ-командой

Статус: **план реализации**, 2026-11-01. Не означает реализованные возможности, результаты тестов или развёртывание.
Основной принцип: один разговор для владельца бизнеса; диспетчер понимает запрос и контекст, детерминированный координатор управляет выполнением, CMO включается только для маркетинговой стратегии, специалисты/действующие конвейеры создают артефакты.

**Обязательные предшествующие правила:**
- [ADR-SERVGO-001](https://github.com/grunvald91/booking_bot/blob/main/docs/architecture/SERVGO_SAAS_RULE.md).
- [SaaS roadmap](SERVGO_SAAS_ROADMAP.md): завершить текущий редизайн, затем A (tenant security), B/C (очереди/лимиты), D/E (комплексная координация/UI), F (нагрузка). Локальные улучшения понимания и интерфейса допустимы в пределах редизайна.
- [Первоначальный план диспетчера](../OWNER_HOME_DISPATCHER_PLAN.md), [текущая архитектура](../../ARCHITECTURE.md).
- DeepSeek [dsh-superagent-prototype](https://github.com/deepseek-ai/dsh-superagent-prototype) — **исследовательский образец**, НЕ готовая SaaS-библиотека. Идеи Ticket, Subscription, Mandate, Effects/Outbox, quiet notifications адаптируем, код и права исполнения не переносим напрямую.

## 1. Продуктовый контракт

Владелец может в одной мобильной/десктопной беседе:
1. Спросить факт о текущем бизнесе (при наличии связанного источника), запросить материал или действие, говорить текстом/голосом.
2. Назвать задачу естественно: «видеообъяснение», «рисованное видео», «сделай ролик с рисунками»; система различает *создать*, *показать*, *объяснить*, *написать сценарий*, *отменить*.
3. Продолжить однозначно связанную задачу: «сделай минутным», «измени концовку», «покажи ход», «отмени эту». Изменения должны быть безопасны: до старта — обновление черновика; после старта — проверка возможности пересоздания/ревизии, а не мутация уже запущенного вызова.
4. Заказать несколько работ в одной реплике; получить одно родительское поручение со стадиями, а не бесконтрольную цепь агентских вызовов.
5. Увидеть одно правдивое состояние и ссылку на результат, получить уточняющий вопрос только когда без него нельзя действовать.
6. Не знать названия агентских ролей и разделов. Существующие экраны остаются для детального редактирования, но обычный путь не требует перехода.

Область первого выпуска: **AI Growth OS и существующие конвейеры** (пост, план, рисованное видео, аналитика, материалы). Связь с BookingBot, Mail, Shifts — по отдельным авторизованным адаптерам после tenant security.

## 2. Разделение ответственности

```text
Пользователь/голос/плашка
  -> Dispatcher (намерение + контекст разговора + привязка к заданию + ответ)
  -> CapabilityRegistry + Policy/Authorization (операция, параметры, разрешения, стоимость)
  -> Deterministic Work Coordinator (состояние, очереди, дедупликация, зависимости, события)
      -> простой запрос: существующий сервис
      -> сложный: CMO при необходимости определяет шаги/роли/результаты
          -> существующие Workflows/Workers + Critic с ограничениями
  -> Task/Artifact/ToolCall/CostRecord/Approval + Event/Outbox
  -> исходный чат: карточка, готовый результат, необходимое действие
```

Диспетчер НЕ создаёт новые неподдерживаемые способности модели, НЕ становится узким местом фоновой генерации, НЕ ждёт работу в HTTP. Координатор НЕ принимает маркетинговые решения. CMO НЕ исполняет все роли сам и НЕ дублирует pipeline статьи/видео. Политика и права — только серверный код, не инструкции модели.

## 3. Пошаговое внедрение

### Этап 0 — закончить нынешний редизайн, закрыть явный сбой диспетчера

- Выполнить отдельную проверку [PR #204](https://github.com/grunvald91/Ai_growth_os/pull/204), который распознаёт явные запросы видеообъяснений и передаёт их в **существующий** whiteboard/approval flow; проверить ситуацию «сделаем объяснение» по контексту: без слова «видео» нельзя автоматически заказывать платную генерацию без однозначной предыстории.
- Исправить ложную формулировку «не понял», когда фактически упала модель или JSON невалиден; различать provider timeout, parse, unsupported и недостаток параметров.
- Тесты: текст/голос, вариации русских фраз, отсутствие модели, одна карточка подтверждения, отмена, повтор client_key.
- Merge/deploy только после одного целевого CI и проверки сочетаемости с текущими UI-ветками; не расходовать Actions на повторные одинаковые проверки.

**Готово:** типовые существующие команды работают в чате; при ошибке понятна причина и есть повтор без двойного расхода.

### Этап 1 — надёжное понимание и связь реплик с задачами (не создаёт новый исполнительный движок)

- Ввести формализованное решение `answer|read|start|modify|status|cancel|confirm|clarify|unsupported` с `capability_id`, типизированными параметрами, `target_task_id` (при необходимости), признаком полноты и кодом причины; JSON модели валидировать сервером.
- Применить последовательность: проверенная безопасная команда/чип → явно указанный task_id → единственная релевантная активная задача с подтверждённой контекстной связью → структурированная LLM-классификация → один вопрос при неоднозначности. Сходство темы **не** даёт право привязать сообщение к чужому или неочевидному заданию.
- Не пытаться закрыть свободный русский множеством регулярных выражений: узкие fast paths + LLM по актуальному реестру + регрессионный набор реальных, обезличенных обращений.
- Сохранять историю связей сообщения и задания; добавить структуру ассоциаций при необходимости, не перегружать поле `dispatcher_messages.task_id` для нескольких дочерних работ.
- Ввести набор eval: синонимы, опечатки STT, отрицание, «только сценарий», «покажи готовое», продолжение/новая тема, мультимодальные входы по фактической поддержке; не заявлять поддержку файлов, пока ingestion не реализован.
- Позиционирование ошибок: недоступность диспетчера — не «непонятный пользователь».

**Готово:** «сделай ролик → переделай концовку → покажи статус» однозначно относится к одной работе и не создаёт второй при повторе; при двух подходящих задачах задаётся вопрос.

### Этап 2 — tenant security и полноценный жизненный цикл заданий (SaaS A)

- Существующие `Task`, `Artifact`, `DispatcherConversation`, `DispatcherMessage`, `ToolCall` использовать как первичные сущности; проверить, нужна ли таблица `work_item`/связь `message_task_link` и версия спецификации (`task_revision`) прежде чем мигрировать БД.
- Для каждой операции: tenant/product_id + account + разрешённый сервис + ссылка на исходное сообщение + ключ идемпотентности + текущая версия требований.
- Серверная авторизация до чтения, изменения, отмены, утверждения и получения артефактов. Проверка также при background execution и повторном запуске.
- Логически разделить состояние приёма задания от работы исполнителя. Целевые состояния: `draft/needs_input/needs_approval/queued/running/blocked/partially_completed/completed/failed/cancelled`. Не внедрять новые статусы в старую таблицу без таблицы совместимости.
- Ревизии сохранять отдельно; менять параметры активной оплачиваемой операции без проверки нельзя.

**Готово:** бизнес A не видит и не меняет B; уточнения и версии спецификации аудируются; подтверждение относится к конкретной версии и владельцу.

### Этап 3 — надёжные очереди и расходы (SaaS B/C, перед универсальной координацией)

- Зафиксировать transactional outbox для запуска/перехода состояния/доставки результата; события после commit, с уникальными ключами и ограниченными retry/backoff.
- Согласовать идентичность повторов от браузера/HTTP/worker/провайдера и явные ветви для неопределённого внешнего результата; не обещать exactly-once внешнего API без его поддержки.
- Claim/lease/heartbeat, retry policy и восстановление после рестарта на текущем PostgreSQL/worker; без нового брокера до измеренной необходимости.
- Per-tenant и глобальные ограничения конкурентных тяжёлых операций, приоритет интерактивных запросов, fair scheduling.
- Оценка до платного шага, резервирование лимита, учёт всех фактических попыток и критика, отдельные расходы компании и задания.
- Использовать существующие `CostRecord`/Policy, не добавлять обязательные согласования публикаций там, где уже утверждён автоматический режим. Подтверждение дорогостоящего видео сохраняется.

**Готово:** перезапуск не теряет работу; повтор не плодит платные задачи; один бизнес не блокирует других; расходы отражены корректно.

### Этап 4 — координатор составных поручений (SaaS D)

- Добавить `WorkCoordinator` как **детерминированный слой** поверх существующих `Task`, `Task.parent_id` и специализированных воркеров, а не второго LLM-руководителя.
- Вход: типизированная цель, контекст бизнеса, разрешённые capabilities, стоимость/лимиты, требуемый результат. Выход: валидация допустимых шагов с зависимостями, статусами и артефактами.
- Простое поручение сразу направлять в существующий pipeline. Для комплексного CMO/руководитель направления предлагает только необходимые стадии (например, анализ аудитории → план → посты и рисованное видео → критик → результат).
- Проверять роль и тип задания (`ROLE_TASKS`), DAG без циклов, tenant и budget до enqueue; ограничить глубину, fan-out, число повторов и возвращений к CMO.
- Поддержать остановку, доработку, частичный успех и возобновление без перезапуска успешно завершённых этапов.
- Научные/фактологические видео: отдельная проверка утверждений и источников до озвучки/рендера. Ошибка фактов возвращает материал на доработку с ограниченным числом попыток.

**Готово:** одно комплексное поручение возвращает набор корректных артефактов; при частичном сбое не утверждает, что всё готово, и не перезапускает уже успешные шаги.

### Этап 5 — один чат и управление ходом работы (SaaS E)

- Переиспользовать существующие блоки `task`, `material`, `links`, `confirm`; для составной работы — одна компактная карточка с подэтапами.
- Готовое и состояния «нужен ответ / готово / ошибка» появляются в исходной беседе; промежуточные стадии обновляют карточку, а не создают десятки сообщений.
- Действия рядом с карточкой: `Продолжить`, `Уточнить`, `Посмотреть`, `Отменить`, `Повторить сбойный этап`; показывать только допустимые в данном состоянии.
- Сохранять состояние разговора между устройствами. На телефоне ввод, клавиатура, кнопка микрофона, кнопки подтверждения и лента не перекрывают друг друга.
- Доставка через outbox; SMS/email/TG уведомления только через разрешённые каналы и настройки.

**Готово:** владелец проходит полный путь запроса и доработки без обязательной навигации по студии, видит одно правдивое состояние, а потери/дубли уведомлений контролируются.

### Этап 6 — сервисы всей платформы (постепенно)

- Добавить авторизованные адаптеры BookingBot (расписание, свободные окна, клиенты, перенос/отмена), Mail (черновик/рассылка/отчёт), Shifts (смены, табель), Growth (контент и аналитика).
- Реестр возможностей включает `domain/action/schema/side_effect/cost/auth/version`. Не подключённый модуль отвечает честно «данных нет» или предлагает переход.
- Канонически сопоставлять `business_id` BookingBot ↔ `product_id` Growth через подтверждённую принадлежность; не смешивать UUID/учётные записи.
- Чувствительные операции требуют явных прав и применяют действующую продуктовую политику без лишних подтверждений.

**Готово:** конкретные запросы поддерживаются через контрактные адаптеры без доступа к данным другого бизнеса.

### Этап 7 — выпуск и наблюдаемость (SaaS F по фактической нагрузке)

- Тесты: семантическая регрессия, безопасность `A/B`, модель недоступна, два одновременных сообщения, перезапуск после enqueue/до результата, расходы и завершение без duplicate notifications.
- Метрики: доля корректно классифицированных задач, доля уточнений/ложных запусков, p50/p95 диспетчера, время в очереди, completion, retries, cost per task и per tenant.
- Поэтапное включение флагом для ограниченного набора бизнесов, возврат к прежней маршрутизации без удаления данных; полноценные нагрузочные испытания только перед масштабированием.
- Не использовать отдельные GitHub Actions на каждый мелкий коммит. Целевые локальные проверки → один обоснованный CI/PR → merge → выпуск → короткий production smoke.

**Готово:** критерии приёмки подтверждены тестами и наблюдением на реальной версии. Число поддерживаемых бизнесов определяется измерениями.

## 4. Первая вертикальная демонстрация

1. Владелец: «Сделай рисованное видеообъяснение, почему горячий предмет массивнее холодного».
2. Диспетчер сохраняет исходный запрос, распознаёт capability, извлекает тему. Дорогая генерация ещё не запущена.
3. Показывается карточка темы/длительности/платности. Пользователь: «Сделай на минуту».
4. Диспетчер обновляет **тот же черновик/версию** и показывает новые параметры. Подтверждение относится только к последней версии.
5. После подтверждения координатор запускает существующее whiteboard workflow. Научный факт проходит фактчекинг по источникам до рендера.
6. Чат показывает состояние; затем одну готовую карточку с просмотром, исправлением и ссылкой. Доработка использует то же поручение и новую версию, но не повторяет неизменившиеся дорогие стадии без причины.
7. Повтор одинакового client_key не создаёт дублей; другой бизнес не видит ни файл, ни карточку.
