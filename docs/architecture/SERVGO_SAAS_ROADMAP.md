# План поэтапной реализации SaaS-архитектуры и оркестрации ServGo

**Дата согласования правила:** 2026-11-01.  
**Статус:** утверждено архитектурное правило; этот документ — согласованная последовательность будущих работ, **не отчёт о реализации пунктов**.  
**Приоритет:** сначала завершить текущий редизайн; SaaS-доработки выполнять небольшими задачами вместе с развитием затронутых модулей. Не запускать отдельный большой рефакторинг, миграцию или деплой только из-за этого документа.

**Нормативный источник:** [ADR-SERVGO-001 — Обязательное правило SaaS](https://github.com/grunvald91/booking_bot/blob/main/docs/architecture/SERVGO_SAAS_RULE.md).

> ServGo — многопользовательская SaaS-платформа с общей масштабируемой инфраструктурой и изолированными рабочими пространствами бизнесов. Все модули, агенты, очереди, интеграции и оркестрационные процессы проектируются так, чтобы параллельная работа множества компаний не приводила к смешиванию данных, неконтролируемому расходованию ресурсов или блокировке работы других клиентов.

## 0. Очередность и нецели

**Первая активная задача — закончить редизайн**. Не отвлекать команду на переустройство фоновых исполнителей, инфраструктуры и схем БД, пока UI/UX-работы не завершены; исключение — подтверждённые ошибки доступа к чужим данным или другие критические дефекты.

В приоритете редизайна (готовность определяется отдельно в текущих задачах, здесь не объявляется):
- мобильный и десктопный клиентский путь и админка записи; корректное продолжение уже выбранной услуги/мастера;
- дизайн Growth Studio: единая история, плавающие прозрачные элементы, естественные карточки, корректная хронология, голосовой и текстовый ввод, понятные ошибки;
- адаптивность модулей и согласованный PWA-переход Growth/Mail; проверка при рабочей клавиатуре, навигации и возврате из ссылок;
- достаточные функциональные и браузерные проверки изменённых экранов, затем релиз и сверка production.

**Не делаем сейчас:** новый кластер, Temporal, микросервисы, массовый перенос данных, универсальный ИИ-оркестратор, изменение всех тарифов, переписывание уже работающих конвейеров или лишние проверки ради формального процента покрытия.

## 1. Реальная исходная база (зафиксирована по main на 2026-11-01)

- `app/models/domain.py`: Task, Artifact, Goal, Approval, CostRecord и прочие сущности содержат `product_id`, Task имеет `parent_id`, но нет общего графа зависимостей.
- `app/api/content_studio_auth.py`: доступ к компаниям ограничивается разрешёнными `studio_product_ids`; требуется отдельная проверка всех фоновых путей и межмодульных соответствий.
- `app/dispatcher/models.py` и `service.py`: история привязана к компании/аккаунту; `client_key` — средство дедупликации сообщения, не гарантия exactly-once для всех побочных действий.
- `app/team_worker.py`, `app/insights/specialists.py`, `app/content/worker.py`: разные очереди и циклы, часть выборок глобальна по приоритету/дате; справедливость между бизнесами и многопроцессный claim не подтверждены для всей системы.
- `app/workflows/daily_growth_review.py`: CMO формирует стратегические решения и дочерние задания, но не универсальный обработчик любых запросов.
- `app/workflows/team_cycle.py`: матрица допустимых ролей и типов задач, последовательное выполнение; `followup_cmo` не должен бесконечно порождать новые работы.
- `app/workflows/research_department.py`: есть специализированный fan-out/fan-in и итоговый отчёт для исследований; повторно использовать, не дублировать.
- `app/llm/model_router.py`: имеются модели, приоритеты и оценка лимита **за вызов**, но не полный периодический бюджет компании.
- `app/llm/critic.py`: критик работает с отдельными черновиками и иногда пропускает проверку; не считать проверку итоговой композиции универсально выполненной.
- `app/dispatcher/blocks.py`: есть текст, карточки задач/материалов, ресурсы, таблицы, подтверждения; для составной работы при необходимости добавить один компактный тип.

**Нельзя заключать из этого, что сервер уже выдерживает N компаний**: текущая пропускная способность, квоты провайдеров и реальные SLO должны измеряться.

## 2. Правило попутной реализации (для каждой следующей задачи)

1. Реализовать запрошенную функцию/редизайн **без расширения объёма** на всю платформу.
2. Проверить только затронутые SaaS-инварианты: `product_id/business_id` и права, контекст/файлы/кэш, очередь/повторы/стоимость, отсутствие блокировки соседних бизнесов.
3. Исправить выявленное нарушение в рамках этого изменения, либо завести конкретный пункт ниже с причиной отсрочки. **Утечки доступа между компаниями никогда не откладывать.**
4. Добавить минимальные целевые тесты `business A / business B`, двойной запрос и сбой во время выполнения, если эта ветка кода затронута.
5. В отчёте указать «SaaS: проверено / требует отдельного этапа» с проверяемыми фактами. Не заявлять готовность к тысячам бизнесов без испытаний.

Это не требование каждый раз выполнять нагрузочный тест всего сервера и не повод задерживать маленькие UI-изменения.

## 3. Этапы после завершения редизайна

### Этап A — карта бизнес-контекстов и безопасность (приоритет P0 после редизайна)

**Где:** BookingBot, Growth, Mail, Shifts, SSO/MCP, новые модули.

- Инвентаризировать бизнес-идентификаторы и server-side связи; формализовать маппинг BookingBot `business_id` ↔ Growth `product_id` через проверенные разрешения, без подмены одним UUID.
- Проверить чтение/запись, файлы, кеширование, внутренние вызовы, подписки, задачи и артефакты на межарендную изоляцию.
- Права на задания проверять и при создании, и при чтении результата, и в фоне. Контекст для LLM собирать минимально под задачу; исключить перенос чужого контекста в памяти worker.
- Добавить регрессионный набор: бизнес A не видит/не запускает/не отменяет задачи бизнеса B даже по известному ID.

**Готово, когда:** тесты изоляции проходят по всем изменённым путям; найденные нарушения устранены. Наличие `product_id` само по себе не закрывает этот этап.

### Этап B — надёжные очереди и справедливая конкуренция (P1)

**Где:** общий цикл worker, контент, SEO, исследования, видео.

- Инвентаризировать реально работающие обработчики и их классы нагрузки: короткие интерактивные запросы отдельно от длительного рендеринга/SEO.
- Ввести общий протокол постановки/захвата задач: идемпотентность, атомарный claim, lease/heartbeat, проверяемые retry, dead-letter/failed, отмена, восстановление после рестарта.
- Планирование по компаниям: bounded concurrency для каждого бизнеса и глобально, fair scheduling без starvation, приоритет внутри класса; понятное состояние очереди пользователю.
- Сохранить существующие конвейеры и результат/артефакты: переделывать адаптеры захвата по одному, не одномоментно.
- Использовать возможности текущего PostgreSQL и worker, если они удовлетворяют измеренным требованиям; добавлять брокер только при обоснованной нагрузке.
- Не обещать exactly-once внешней публикации без внешнего ключа идемпотентности и механизма восстановления неопределённого исхода.

**Готово, когда:** имитация одновременных заданий нескольких бизнесов не создаёт дублей и не даёт одному бизнесу заблокировать остальных; перезапуск worker не теряет ни заявку, ни статус.

### Этап C — расходы, квоты, тарифы и приоритеты (P1, совместно с B)

- Ограничения **на бизнес** (число одновременных задач, дневной/месячный допустимый расход, тяжёлые видео) и **на составную задачу** (число вызовов, глубина, бюджет).
- Проверять остаток до дорогого запуска и записывать фактический расход после ответа, отдельно отслеживать стоимость с неизвестной ценой.
- Не изменять существующие тарифы без продуктового решения владельца; сначала определить модель измерения и технические предохранители.
- Сообщать о превышении пределов конкретно и без фиктивной «нулевой стоимости».
- Следить, чтобы автоматические критики, повторные вызовы и fallback учитывались в том же бюджете задания.

**Готово, когда:** параллельные задания бизнеса не могут обойти его лимит конкурирующими резервированиями; расходы одного бизнеса не смешиваются с другим.

### Этап D — универсальный координатор для комплексных маркетинговых задач (P2)

**Схема:** владелец → диспетчер (что требуется) → координатор (состояние и маршруты) → CMO при необходимости (план маркетинга) → действующие специалисты/конвейеры → сборка → проверка → итог владельцу.

- Диспетчер использует реестр реально исполнимых действий, не обещает несуществующих агентов и не начинает платную цепочку ради простого вопроса.
- Простой запрос выполняется напрямую; существующий конвейер поста/статьи/видео используется целиком, без повторной собственной редакторской цепочки.
- Для комплексного запроса CMO/руководитель направления определяет только необходимые этапы, роли, ожидаемые артефакты, критерии готовности, ограничения по стоимости. Не путать CMO с инфраструктурным scheduler.
- Код валидирует граф зависимостей, принадлежность бизнеса, поддерживаемые `ROLE_TASKS` и права, отсеивает циклы и недоступные роли **до** постановки в очередь.
- Координатор возобновляет исполнимые этапы через существующие worker, хранит однозначный итоговый статус (ожидает/выполняется/частично/готово/ошибка/отменено).
- Сборка использует источники созданных артефактов; критик проверяет только существенные дефекты итогового результата и возвращает исходный валидный вариант при недоступности проверки с явным состоянием.
- Запрещено бесконтрольное разрастание CMO → агент → CMO и бесконечные переделки. Повторы, фан-аут и вложенность ограничены бюджетом и критериями работы.
- Поддерживать продолжение в другой сессии и просмотр результата тем же бизнесом; не ждать длинную генерацию внутри HTTP-запроса.

**Готово, когда:** одна составная задача проходит штатный путь, не размножает запросы при повторе, корректно деградирует при частичном сбое и возвращает сборный результат только своей компании.

### Этап E — единый интерфейс результата (P2 вместе с D)

- Переиспользовать `text`, `task`, `material`, `resource_list`, `links` и таблицы; не создавать новый виджет без нужды.
- Для составной работы — один компактный блок с названием, кратким состоянием, этапами и ссылкой на итог; он обновляется по ID, не спамит новыми сообщениями при каждом progress update.
- В чате — короткое человеческое резюме; полный материал/видео/план — по соответствующей ссылке или встроенным просмотром.
- Соблюдать действующий ServGo Air: mobile-first, элементы управления визуально плавают без общей окрашенной подложки, область прокрутки не перекрывается.

**Готово, когда:** данные и статус одной работы не дублируются, последнее обновление видно внизу хронологии, результат корректно читается на телефоне.

### Этап F — нагрузочные испытания и масштабирование по измерениям (P2/P3, до широкого выхода на рынок)

- Определить измеримые SLO (p50/p95 для диспетчера, ожидание по классам задач, доля успешного выполнения, частота повторов, расход и fairness). Пороговые значения выбрать по реальным требованиям бизнеса и возможностям провайдеров, а не выдумывать сейчас.
- Построить сценарии смешанной нагрузки: разные компании одновременно задают вопросы, генерируют посты, запускают SEO/видео и завершают цепочки после перезапуска.
- Проверить конкуренцию нескольких worker на PostgreSQL, нагрузку DB connection pool, задержки и квоты внешних моделей; при необходимости добавить worker-реплики и ресурсные ограничения.
- Проверить отсутствие чужих данных в результатах, логах, кэше, подписках и retry во время нагрузки.
- Решение о Redis/RabbitMQ/Temporal/Kubernetes принимать только после измеренного ограничения, с оценкой сложности обслуживания и стоимости.

**Готово, когда:** подтверждены целевые SLO на согласованном количестве одновременно активных компаний и измерен запас ресурсов. До этого ни «1000», ни «10 000 бизнесов» не заявлять как доказанную вместимость.

## 4. Стандартные проверки для PR, затрагивающего работу с бизнесами

Минимально необходимые критерии (применять по релевантности):
1. **Tenant scope**: A не читает/не меняет B через прямой API, внутренний сервис, ID файла, фоновые задачи и результаты.
2. **Retry**: повтор сообщения/задачи с тем же ключом не создаёт новую платную операцию.
3. **Concurrency**: два worker не выполняют одну задачу; один тяжёлый бизнес не монополизирует класс ресурса.
4. **Recovery**: сбой до/после запроса провайдеру оставляет корректное состояние и допускает безопасный restart/compensation.
5. **Cost**: ограничения до вызова, учёт авторских/критических/fallback-попыток, отдельные расходы компании.
6. **Correct output**: нужный артефакт, корректные ссылки и права, отсутствие фиктивного «готово» при частичном сбое.
7. **Security of actions**: внешние публикации, рассылки и изменения по действующей политике, без добавления новых согласований там, где владелец утвердил автоматический режим.
8. **Mobile UX**: где UI затронут — ширина телефона, прокрутка, голос/клавиатура, отсутствие дублирования и скрытых кнопок.

**Не запускать полный комплекс по каждой мелкой правке.** Применять целевые проверки к затронутому компоненту, обязательные CI и один обоснованный интеграционный прогон при пересечении границ модулей.

## 5. Как выполнять этот план постепенно

- У каждой новой задачи в описании отмечать, какой SaaS-инвариант затронут. Если никакой — не расширять объём работы.
- При затрагивании очереди сначала выполнять пункт этапа B; при запуске платной модели — релевантную часть C; при добавлении оркестрируемой работы — D; при интерфейсе результата — E.
- Поддерживать отдельный backlog на ещё не затронутые участки (не превращать в блокер текущего редизайна). По окончании редизайна сначала A, затем B/C, затем D/E, затем F.
- Для каждого этапа отдельно: анализ существующего кода → минимальный план и проверка → небольшая ветка/PR → тесты → merge → безопасный выпуск. Не смешивать с незавершёнными UI-ветками.
- Статус работы менять только по фактам тестов и деплоя; документация сама по себе не означает реализованный функционал.
