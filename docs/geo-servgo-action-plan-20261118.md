# ServGo · GEO-план для SEO-завода и публичных сайтов

Дата анализа: 2026-11-18. Статус: **план работ, а не утверждение о состоянии production**.

Основа: [Иван Юницкий, «GEO простыми словами, как сайту попасть в ответы нейросетей», vc.ru, 16.11.2026](https://vc.ru/ai/3259633-geo-dlya-sayta-kak-popast-v-otvety-nevrossetey). Опыт автора с одним сайтом не является доказательством универсального эффекта. Проверка рекомендаций: [Google Search Central AI features](https://developers.google.com/search/docs/appearance/ai-features), [Яндекс: Видимость в Алисе AI](https://yandex.ru/support/webmaster/ru/service/alice-answers), [Bing IndexNow](https://www.bing.com/indexnow/getstarted), [OpenAI Publishers FAQ](https://help.openai.com/en/articles/12627856-publishers-and-developers-faq).

## Цель и область
- Два публичных режима: блог ServGo на \`servgo.ru/blog/...\` и блоги подключённых организаций на \`servgo.ru/business/{id}/blog/...\`.
- Не создавать «GEO-страницы ради баллов»: оптимизировать узнаваемость источника, полезность и реальные заявки.
- Не путать **доступность для обхода**, **индексацию/цитирование**, **переходы**, **заявки**. Каждому сигналу — отдельное поле со статусом источника. Значение \`unknown\` не подменять нулём.
- Выпускать изменения постепенно на ServGo; после проверки переносить в tenant-scoped сайты компаний без смешивания данных.

## Что уже есть в коде — не строить повторно

1. Публичный SSR-блог, canonical, метаданные и \`BlogPosting\` для ServGo: \`services/booking_bot/webapp/templates/blog.html\`.
2. Публичные страницы и XML sitemap для бизнесов, \`datePublished\`/разметка: \`services/booking_bot/web/api/routes/seo_pages.py\`.
3. \`robots.txt\` и ссылки на sitemap: \`services/booking_bot/web/frontend/public/robots.txt\`.
4. Сохранение \`direct_answer\`, \`FAQ\` и \`meta_description\` в генерации: \`app/workflows/article_production.py\`, \`app/workflows/article_contracts.py\`.
5. Google Search Console и Яндекс Вебмастер (когда владельцем даны доступы): \`app/seo/search_metrics.py\`; пустые подключения уже имеют явный статус.
6. Подготовка отдельных текстовых адаптаций для \`vc_ru\`, \`dzen\`, \`telegram\`: рабочий генератор и contracts (это **не подтверждение** существования автопубликации).

Перед любым изменением проверить на реальном окружении, как и на какой версии сервера работают эти компоненты.

## P0 — доступность источников для поисковых/AI-ботов и людей

**Задача.** Режим «Проверка GEO-доступности» для двух типов URL (главный блог и каждый публичный блог компании).

Проверять \`robots.txt\`, \`sitemap.xml\`, HTTP, цепочки редиректов, сертификат, canonical, \`noindex\`, действительность HTML и полноту текста; с User-Agent \`Googlebot\`, \`YandexBot\`, \`OAI-SearchBot\`, \`ChatGPT-User\`, \`PerplexityBot\`, \`Claude-User\` и обычным браузером. Проверять с целевой географии читателя; не делать геоблокировки частью обхода. **User-Agent легко подделать:** такой curl — тест реакции сайта на заголовок, а не доказательство личности настоящего бота. Для логов верифицировать IP по официальным диапазонам и политике соответствующего поисковика, где возможно.

**Критерий готовности.** HTTP 200 с реальным индексируемым HTML на публичных канонических страницах, без дискриминационного 403/429 и ненужных JS-заглушек; устойчивые sitemap/canonical; отдельные подтверждённые результаты с датой, URL, регионом, статусом.

**Безопасность.** Не открывать /studio, личные кабинеты, приватные материалы или API только ради ботов. Приоритет публичных URL.

## P1 — содержание и авторство, которые можно проверить и процитировать

1. Материалы по реальным информационным вопросам клиентов, из Яндекса/Google, без массового клонирования почти одинаковых статей. Для каждого: подтверждённый запрос, интент, доказательства компании, автор/источник/дата, уникальная польза.
2. Формат «вопрос → короткий самостоятельный ответ (2–3 предложения) → шаги/примеры/проверенные цифры → ограничения». Уже существующие \`direct_answer\` и \`FAQ\` использовать по делу, а не генерировать обязательное количество «для SEO».
3. \`BlogPosting\` / \`Organization\` / \`Person\`: связать статью с **реальным** автором (если известен) и компанией, \`publisher\`, \`mainEntityOfPage\`. Не создавать фиктивные персоналии или ссылки-профили. Одного \`schema.org\` недостаточно для AI-цитирования.
4. Даты \`datePublished\` и \`dateModified\`, видимые читателю, в JSON-LD и sitemap должны происходить из событий публикации/содержательной правки. Не «освежать» дату по расписанию без фактической правки.
5. Финальный критик проверяет не только формат, но и точные источники, отличия от уже опубликованных статей, содержательность и соответствие запросу. Сохранять человеческое согласование для неподтверждённых фактов.

**Критерий готовности.** Один набор данных статьи одинаково представлен пользователю, поисковому боту, JSON-LD и sitemap; нельзя увидеть подтверждение несуществующего автора/даты или недоказанный факт.

## P2 — уведомление об изменениях и дистрибуция

1. Подключить **IndexNow** для новых, существенно изменённых и удалённых **публичных** URL после успешной транзакции публикации. Ключ размещён на соответствующем публичном хосте; домен/права проверяются. Уведомления идемпотентны, с очередью, retry, ограничениями провайдера и отчетом статусов 200/202/4xx/5xx. **Успешное отправление ≠ проиндексировано.** Google не участвует в IndexNow, для него sitemap и Search Console.
2. Для релевантных материалов делать адаптированные кросспосты на vc.ru, Дзен (и Хабр лишь где допустимо правилами и аудиторией). Не копировать слепо: уникальный заход/структура/контекст, точная ссылка на оригинал и UTM-атрибуция. Внешняя площадка может ранжироваться выше оригинала — это измерять отдельно.
3. Отправка от имени компании требует явно подключенного канала, проверенных API/прав и решения владельца; текстовая адаптация ≠ размещённый пост.
4. Установить внутреннюю перелинковку из ответа на полезные смежные материалы и страницу услуги, без ссылочного спама.

## P3 — измерение GEO на фактах

Единый экран SEO/GEO с раздельными источниками:
- **Технический охват:** реальные HTTP-логи публичных страниц (бот/браузер/IP-верификация, status, URL, дата, регион без хранения лишних персональных данных), Search Console URL Inspection, Вебмастер; различать bot crawl и user-triggered fetch.
- **Присутствие в ответах:** доступный отчет «Видимость сайта в Алисе AI» (если подключён и данные есть), проверяемые вручную с примерами ответов ссылки/упоминания, возможности Bing AI Performance при подтверждённом доступе. Обычный заход OAI-SearchBot не подтверждает цитату ChatGPT.
- **Результат:** Google/Yandex clicks/impressions (если доступны), переходы с \`utm_source=chatgpt.com\` и других AI/referral (не каждый приход определяется только referrer), переходы с vc.ru/Дзен, заявки/регистрации/оплаты с атрибуцией.
- **Порядок приоритета:** продажи и заявки → живые посещения → поисковые клики → AI-упоминания → показы и позиции. Не создавать недостоверный единый GEO-score.
- **Сравнения:** полные совпадающие окна по дням недели и географии; явные аномалии, неизвестные данные и причинные альтернативы. Нет показателя — нет вывода «упало/выросло».

## P4 — автономный агент и эксперименты

- Лёгкие ежедневные детерминированные проверки: доступность сайта/ботов, новые ошибки индексации, sitemap, технический трафик и события воронки. Проблемы — в задачи владельцу, без скрытого платного перебора контента.
- Еженедельный отчёт по конкретной компании: 3–4 подтверждённых показателя, причины/неопределённости, конкретные действия («исправить», «обновить», «опубликовать», «проверить»).
- Реестр гипотез: baseline, одна правка за раз, дата контрольной проверки, критерий успеха и отката. При незавершённом тесте нельзя хаотично переписывать эту же страницу.
- Авторизационные границы \`tenant_id\`; никакие логи других компаний, секреты и номера клиентов не передавать в модель.
- При сборке материалов/команд автоматически исключать похожие на API-ключи и секреты строки из примеров.

## Проверяемый порядок работ

| Приоритет | Задача | Результат | Приёмочный тест |
|---|---|---|---|
| P0.1 | Public crawl gate | матрица \`URL × UA × регион × HTTP/robots/canonical\` | 200 с контентом; честный 403/ошибка в отчёте |
| P0.2 | Sitemap/indexing audit | публичные URL и метаданные без дублей | published URLs only, consistent canonical, no ghost entries |
| P1.1 | Author/date/JSON-LD alignment | достоверное авторство и дата правки | единственный источник фактов для HTML+JSON-LD+XML |
| P1.2 | Контентный бриф и уникальность | полезные самостоятельные ответы | нет выдуманных фактов/FAQ/дублированных статей |
| P2.1 | IndexNow outbox | доставленные события publish/update/delete | атомарное событие, retry, без дублирующей отправки |
| P2.2 | Кросспосты | согласованные адаптации и исходная ссылка | подтвержденная публикация и атрибуция |
| P3.1 | GEO metrics | четыре отдельные группы метрик и статусы источников | no synthetic citations/traffic, tenant scope |
| P4.1 | SEO/GEO watchdog + гипотезы | короткий отчёт и задачи вместо циклов «ИИ пишет ИИ» | детерминированная диагностика, стоп при технических ошибках |

## Не включать в KPI без доказательств

- \`llms.txt\` как рычаг цитирования (уже существующий файл можно оставить как карту сайта);
- обещания роста ChatGPT/Google citations от произвольного \`schema.org\`;
- «баллы GEO» и публикацию сотен слабых страниц;
- объявления о цитировании AI по одному заходу бота в логах;
- утверждения, что IndexNow гарантирует индексацию;
- автоматическое размножение чужого контента и обновление \`dateModified\` без правок.

**Контрольная метрика успеха пилота:** за 28 дней сравнить реальные заявки, живые визиты, индексированные качественные страницы и проверяемое присутствие в AI-ответах с исходными 28 днями, со статусом доступности каждой метрики и перечнем альтернативных причин изменений. Порог «роста» до сбора baseline не обещать.
