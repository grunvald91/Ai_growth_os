# Главная growth.servgo.ru: единая строка и диспетчер — архитектура и план

Статус: проект (design), 2026-10-22. Это план, а не реализация. Он развивает видение из
`docs/OWNER_INTERFACE_AND_INSIGHTS.md` (17.10.2026) и опирается на то, что реально есть в коде на `main`.
Всё, что здесь названо «решением», — это предложение до подтверждения владельцем. Нерешённое вынесено в раздел 11.

## 1. Что строим

Одна главная страница, через которую владелец делает всё: просит, спрашивает, смотрит результат, переходит
в нужное место платформы. Страница состоит из трёх частей:

1. **Строка ввода** — писать текстом или надиктовать голосом; рядом переключатель в режим общения.
2. **Подсказки** — одна–две строки плашек вдоль строки ввода с тем, что владельцу сейчас нужнее всего.
3. **Область ответа** — под строкой: текст диспетчера, кнопки и плашки-ссылки на страницы платформы, таблицы,
   карточки заданий, предпросмотр материалов.

Принцип: владельцу не нужно знать, где что находится и какой агент за что отвечает. Он говорит, что хочет;
диспетчер сам решает, ответить, переспросить или передать работу команде, и всегда сообщает, что именно сделал.

### Что изменилось по сравнению с заметками от 17.10

- **Голос** в заметках был отложен до появления платящих клиентов. Теперь владелец хочет его в плане, поэтому
  он включён отдельным этапом (этап 3), а строка ввода проектируется так, чтобы голос был просто ещё одним
  способом получить текст.
- **Режим общения** добавлен как явная часть интерфейса (см. раздел 5, нужно подтвердить трактовку).
- Остальное остаётся в силе: диспетчер — отдельный слой над CMO; подсказки строятся из состояния бизнеса и
  фонового анализа; факты проходят путь «гипотеза → факт».

Проверено по `main` на 22.10.2026.

| Что есть | Где | Как используем |

| Раздача статических файлов | страница «ИИ-команда» отдаёт отдельные `index.html`, `team.css`, `team.js` | Тот же приём для главной, без раздувания Python-строк с CSS/JS |
| Второй процесс-воркер | `app/team_worker.py` | Место для фонового анализа по расписанию (этап 4) |
| Сущности для аудита | `Task`, `AgentRun`, `Artifact`, `Decision`, `Approval`, `ToolCall`, `CostRecord` | Каждый ход диспетчера и каждое его действие записываются через них |

### Чего нет (и это влияет на план)

- **Нет распознавания речи.** В коде есть только озвучка для видео. Голосовой ввод — новая интеграция.
- **Нет связи с данными записей ServGo** (ни настроек, ни клиента к API платформы записи). Значит, подсказки
  про пустые слоты (раздел 3 заметок) невозможны, пока не появится доступ к данным `booking_bot`. На первых
  этапах подсказки строятся только из состояния маркетинга.
- **Нет хранилища диалога.** Нужны таблицы для разговоров и сообщений.
- **Нет потоковой выдачи ответа:** `LLMProvider.generate` возвращает ответ целиком. Первая версия диспетчера —
  один ответ на одно сообщение с индикатором «думаю».

## 3. Архитектура

```text
Владелец (текст / голос)
      |
      v
Главная growth.servgo.ru  ──── подсказки (правила → позже анализ)
      |  POST сообщение
      v
Диспетчер (отдельный слой)
  ├─ контекст бизнеса (профиль + снимок состояния + факты)
  ├─ реестр возможностей (что умеет, риск, исполнитель, страница)
  ├─ решение: ответить / переспросить / передать / показать, где это
  └─ ответ = список типизированных блоков
      |                         |
      | чтение (GREEN)          | задание команде
      v                         v
 сервисы чтения          Task → CMO / специалисты (как сейчас)
      |                         |
      +--- PolicyLayer (GREEN / YELLOW / RED) + Approval ---+
      v
PostgreSQL: разговоры, сообщения, Task, ToolCall, CostRecord, Decision
```

Диспетчер — внутри того же приложения, отдельным модулем, а не отдельным сервисом (правило 8 из `CLAUDE.md`).
Новых серверных компонентов нет: на сервере ServGo мало оперативной памяти, а модель и распознавание речи —
внешние API.

### 3.1. Реестр возможностей — ключевая идея

Каждое умение платформы описывается один раз: название и описание для диспетчера, какие данные нужны,
уровень риска, функция-исполнитель, как показать результат и на какую страницу вести. Диспетчер не «знает»
код — он выбирает из реестра. Добавить новое умение = добавить запись в реестр; диспетчер начинает его
предлагать без переделки.

Первый состав реестра (все исполнители уже существуют):

| Возможность | Риск | Что делает |
|---|---|---|
| Создать материал | GREEN | пост / пакет / видео / сторис / картинка по теме, площадке, аудитории |
| Составить или обновить контент-план | GREEN | ставит задание на план; показывает ссылку на черновик |
| Что сейчас в работе | GREEN | читает задания, показывает карточки со статусом |
| Что ждёт моего решения | GREEN | читает материалы и планы на утверждении |
| Показать материал / план / календарь | GREEN | отдаёт ссылку и короткий предпросмотр |
| Бизнес-разведка | GREEN | запуск исследования конкурентов |
| Утвердить, отправить на доработку | YELLOW | через кнопку подтверждения на карточке |
| Запланировать публикацию в Telegram | YELLOW | только после явного подтверждения |
| Где это находится / как это сделать | GREEN | ссылка на нужную страницу платформы |
| Изменение бюджета, цен, доступов, удаление | RED | не выполняется из строки; диспетчер объясняет, где это делается |

### 3.2. Как диспетчер принимает решение

1. Получает сообщение, последние реплики и контекст бизнеса.
2. Возвращает **структурированное решение** (схема проверяется, а не разбирается из свободного текста): намерение,
   выбранная возможность, найденные параметры, уверенность, что сказать владельцу.
3. Если параметров не хватает или уверенность низкая — **не угадывает**, а задаёт один короткий вопрос и
   сразу предлагает варианты ответа плашками («Для кого пост?» → «Для клиентов салонов», «Для мастеров»).
4. Если действие GREEN — выполняет и сообщает, куда передал («передаю маркетингу — создаю пост»).
5. Если YELLOW — показывает карточку подтверждения; без нажатия кнопки ничего не происходит.
6. Если RED — не делает, ведёт на нужную страницу.

Модель для роли диспетчера выбирается на странице «ИИ-команда» вместе с остальными; для скорости на старте
логично взять быструю модель, а сложный разбор оставить за командой. Нужны жёсткий тайм-аут и запасная
модель: при сбое главная не должна «зависать» (раздел 8).

### 3.3. Блоки ответа

Ответ — это упорядоченный список блоков фиксированных типов. Интерфейс умеет рисовать только их.

| Блок | Для чего |
|---|---|
| Текст | короткое пояснение, без разметки сверх безопасного минимума |
| Плашки-подсказки | варианты следующего сообщения; клик подставляет текст в строку |
| Кнопки-ссылки | переход на страницу платформы |
| Таблица | расписание, список материалов, статусы, итоги |
| Карточка задания | живой статус задания, ссылка на него, результат по готовности |
| Карточка материала | заголовок, фрагмент, кнопки «Утвердить», «Доработать», «Открыть» |
| Карточка подтверждения | YELLOW-действие с кнопками «Подтвердить» и «Изменить» |

Правила безопасности блоков:

- **Цифры и таблицы берутся из сервисов чтения, а не из текста модели.** Модель выбирает, что показать, и
  комментирует; значения подставляет сервер. Так диспетчер не выдумает количество материалов или дату.
- **Ссылки собирает сервер** по реестру возможностей и идентификаторам, а не берёт адрес, написанный моделью.
- Неизвестный тип блока или битая схема отбрасываются; владелец в любом случае получает текст и прямую ссылку.
- Содержимое, пришедшее извне (результаты исследований, комментарии из соцсетей), считается данными:
  оно не может вызвать YELLOW- или RED-действие.

## 4. Контекст бизнеса («знает всё»)

Контекст собирается по ходу запроса из трёх слоёв, а не берётся целиком из базы:

1. **Профиль компании** — версионируемые файлы и утверждённый профиль (как сейчас, правило 3 из `CLAUDE.md`).
2. **Снимок состояния** — компактная сводка: что в работе, что ждёт решения, статус плана, ближайшие публикации,
   последние материалы. Строится детерминированным кодом.
3. **Факты и гипотезы** (этап 4) — подтверждённые закономерности с уровнем уверенности и ссылками на
   доказательства.

Всё проходит через `PrivacyGateway`; ключи и токены в контекст не попадают. Каждый вызов инструмента изолирован
текущей компанией — диспетчер не может увидеть данные другой.

## 5. Интерфейс

### Главная на десктопе

```text
┌ меню ┬──────────────────────────────────────────────┐
│      │  Команда по маркетингу ждёт задание           │
│      │  [ строка ввода                 🎤  💬 ] [→]  │
│      │  [Контент-план] [Пост на тему…] [3 на проверке]│
│      │  ───────────────────────────────────────────  │
│      │  ответ диспетчера: текст, плашки, таблица…    │
└──────┴──────────────────────────────────────────────┘
```

Как в Google: строка вверху, ответ ниже. Страница целиком без прокрутки; если ответ длинный, прокручивается
только область ответа.

### Главная на телефоне

По брендбуку ServGo Air «информация сверху, управление снизу»: сверху лента ответов, внизу, у большого пальца,
строка ввода с кнопками голоса и режима, над ней плашки-подсказки в одну строку с горизонтальной прокруткой,
ниже навигация. Когда диалога ещё нет, приветствие и плашки собираются внизу экрана рядом со строкой.

Расхождение десктопа и телефона намеренное: на десктопе владелец просил «строку сверху, как у Google»,
на телефоне действует правило брендбука. Всё, что доступно на десктопе, доступно и на телефоне.

### Режимы

- **Команда** (по умолчанию): каждое сообщение — запрос, на который диспетчер отвечает блоками.
- **Общение**: непрерывный диалог с историей, видной в области ответа; диспетчер помнит ход разговора.
- **Голос**: нажать микрофон, говорить, остановить. Распознанный текст появляется в строке для проверки и
  правки; отправляет владелец. Так ошибка распознавания не запускает работу.

Существующая главная («Что будем создавать?», «Сейчас создаётся», календарь, пакеты) не удаляется: страницы
остаются доступны через меню и ссылки диспетчера; старый вид можно сохранить как запасной адрес на время
перехода (откат одним переключением).

## 6. Подсказки

Подсказки — отдельный маленький модуль, не часть диспетчера, чтобы они работали быстро и без вызова модели.

Источники и приоритет (чтобы не было взаимоисключающих советов):

1. **Требует внимания** (из состояния): есть материалы на проверке, план ждёт утверждения, задание упало,
   отправку нужно проверить.
2. **Следующий шаг по ходу диалога**: подсказки, которые диспетчер возвращает вместе с ответом; они заменяют
   общие после каждого ответа.
3. **Из анализа** (этап 4): «по вторникам после 18:00 пусто — сделать акцию?».
4. **Постоянные**: «Составить контент-план», «Создать пост на тему…», «Что сейчас в работе».

Холодный старт: пока данных нет, показываются только пункты 1 и 4. Число плашек подгоняется под одну–две строки.
Клик по плашке подставляет текст в строку, Enter отправляет (как в заметках от 17.10).

## 7. Данные и аудит

Предлагаются новые сущности (требуют миграции Alembic):

- **Разговор** — привязан к компании и владельцу; один «текущий» на компанию, кнопка «новая тема».
- **Сообщение** — роль, текст, список блоков, ссылки на созданные задания, модель, время.
- **Ход диспетчера** — принятое решение, возможность, параметры, уверенность.

Связь с существующими сущностями (то, что в заметках называлось «пока не решено»):

- каждое вызванное действие записывается как `ToolCall`;
- передача работы команде создаёт обычный `Task` с пометкой происхождения (диспетчер, номер хода), дальше
  всё идёт как сейчас;
- каждый вызов модели оставляет `CostRecord`;
- важные рекомендации диспетчера записываются как `Decision` со ссылками на доказательства; если доказательств
  нет, набор пустой (правило 10 из `CLAUDE.md`);
- YELLOW-действия подтверждаются через `Approval`.

## 8. Надёжность

- **Сбой или медленная модель:** жёсткий тайм-аут, запасная модель из существующей цепочки; если не ответила и
  она — главная показывает плашки и прямые ссылки («Создать материал», «Мои задания»), а не пустоту.
- **Двойное нажатие и повтор:** задания создаются с ключом дедупликации.
- **Долгие задания:** диспетчер не ждёт их, а выдаёт карточку задания; карточка обновляется через уже
  существующий опрос состояния и по готовности добавляет результат в ленту.
- **Откат:** функция включается переключателем; прежняя главная остаётся доступной.
- **Развёртывание:** на сервере growth.servgo.ru часть правок раньше делалась напрямую и не попала в GitHub.
  Перед выкладкой нужно сверить серверные файлы студии с `main` и выкладывать только перечень изменённых файлов
  через штатный процесс деплоя студии.

## 9. Проверка качества

- Набор эталонных фраз владельца с ожидаемым результатом («нужен контент-план» → возможность «план»;
  «что у меня ждёт?» → список на утверждении; «удали компанию» → RED, объяснение со ссылкой).
- Тесты на фейковом провайдере (`app/llm/fake.py`): схемы блоков, политика GREEN/YELLOW/RED, изоляция компаний,
  идемпотентность, отказ модели.
- Перед включением — небольшой прогон эталонных фраз на живой модели и ручной просмотр владельцем.
- Для интерфейса — проверка на 390 px и десктопе по правилам из `CLAUDE.md`: управляющие элементы на телефоне
  доступны, горизонтальной прокрутки нет.

## 10. Этапы

**Этап 0. Опора (по приоритету из заметок: сначала довести до рабочего).**
Короткий аудит: какие из будущих «возможностей» сейчас работают надёжно. Диспетчер усилит заметность слабых
мест, поэтому в первый реестр попадают только проверенные.

**Этап 1. Каркас, текст и ссылки.**
Новая главная: строка, постоянные подсказки и подсказки из состояния, область ответа. Диспетчер с возможностями
«создать материал», «план», «что в работе», «что ждёт решения», «где это», «переспросить». Блоки: текст, плашки,
кнопки-ссылки, карточка задания. Хранение разговора, `ToolCall`, `CostRecord`, роль «диспетчер» на странице
«ИИ-команда», переключатель и запасной адрес старой главной. Деплой отдельно от остального.

**Этап 2. Богатый ответ и общение.**
Таблицы, карточка материала с «Утвердить / Доработать», карточка подтверждения для YELLOW-действий, режим
общения с историей, подсказки по ходу диалога, возврат результата задания в ленту.

**Этап 3. Голос.**
Запись в браузере, отправка на наш сервер, распознавание через внешний API, текст попадает в строку на проверку.
Распознавание подключается через собственный интерфейс (как `LLMProvider`), чтобы провайдера можно было менять.
Выбор провайдера делается по тесту на реальных русских фразах владельца: качество, цена, доступность из России и
оплата. Какие провайдеры реально поддерживают это через ClaudeHub, не проверено — нужен тест. Микрофон в браузере
работает только по HTTPS (на growth.servgo.ru так и есть).

**Этап 4. Знание о бизнесе.**
Доступ на чтение к данным записей `booking_bot` (занятость слотов), фоновый анализ по расписанию (день, неделя,
две недели, месяц) в воркере, гипотезы и факты, подсказки «из анализа», факты в контексте диспетчера. Подробности
слоёв и рисков — в `OWNER_INTERFACE_AND_INSIGHTS.md`, разделы 4, 5 и 7.

**Этап 5. Дальше.**
Помощь с настройкой бизнеса, предложения без запроса, графики.

## 11. Вопросы к владельцу

Решения, без которых нельзя двигаться, и ограничения, которые не вводятся без согласия владельца.

**Нужно подтвердить:**

1. «Режим общения» — это обычный чат с историей в области ответа (как здесь описано) или голосовой диалог,
   где диспетчер отвечает голосом? Голосовые ответы в план не включены.
2. Клик по плашке только подставляет текст или сразу отправляет? В заметках — подставляет.
3. Какие из существующих функций (контент-план, посты, видео, разведка) сейчас реально работают хорошо?
   От этого зависит состав первого реестра.

**Ограничения, которые не вводятся без ответа:**

- предельная длина голосовой записи;
- сколько прошлых реплик передавать модели (обрезка истории) и как долго хранить разговоры;
- лимит расходов или числа запросов к диспетчеру на компанию;
- хранение аудио: по умолчанию предлагается не сохранять запись после распознавания.
