# Главная growth.servgo.ru: единая строка, диспетчер и голосовой диалог — архитектура и план

Статус: проект (design), 2026-10-22, третья редакция: добавлена связка с платформой записи и общий вход. Это план, а не реализация.
Развивает видение из `docs/OWNER_INTERFACE_AND_INSIGHTS.md` (17.10.2026) и опирается на то, что реально есть
в коде на `main`. «Решения владельца» отмечены явно; остальное — предложения. Нерешённое — в разделе 14.

## 1. Что строим

Одна главная страница, через которую владелец делает всё: просит, спрашивает, смотрит результат, переходит
в нужное место платформы. Три части:

1. **Строка ввода** с двумя способами общения: текст и голосовой диалог.
2. **Подсказки** — одна–две строки плашек с тем, что владельцу сейчас нужнее всего.
3. **Область ответа** — лента разговора: текст диспетчера, плашки, кнопки-ссылки, таблицы, карточки заданий
   и материалов.

Принцип: владельцу не нужно знать, где что находится и какой агент за что отвечает. Он говорит, что хочет;
диспетчер сам решает: ответить, переспросить, передать работу команде или показать, где это. И всегда
сообщает, что именно сделал.

### Решения владельца (22.10.2026)

1. **Режим общения — голосовой диалог:** владелец говорит, диспетчер отвечает голосом (и показывает блоки на экране).
2. **Клик по плашке сразу отправляет** запрос (в заметках от 17.10 было «подставляет в строку» — заменено).
3. **Надёжно работают сейчас:** контент-план, рисованное видео, посты. С них начинается реестр возможностей.
4. **Голосовое «да» подтверждает действие** — в том числе дорогое и YELLOW (с защитой, раздел 6.3). RED голосом
   не подтверждается никогда.
5. **Распознавание речи у иностранного провайдера для ServGo разрешено.** Для клиентов — после юриста (раздел 10).
6. **Связка с расписанием онлайн-записи и общий вход для двух сайтов** входят в план (раздел 7).

Остаётся в силе из 17.10: диспетчер — отдельный слой над CMO; подсказки из состояния и фонового анализа;
факты проходят путь «гипотеза → факт».

### Чего нет и что это значит

- **Нет распознавания речи.** Нужна новая интеграция; какой провайдер подходит, не проверено.
- **Нет потоковой выдачи** (`LLMProvider.generate` отдаёт ответ целиком). В голосовом диалоге это паузы —
  см. раздел 6.4.
- **Нет отмены обычных заданий на контент** (только повтор упавших). Отмена есть у рисованного видео.
- **Нет связи с данными записей ServGo** и нет сопоставления «бизнес в `booking_bot` ↔ компания в студии».
  До этапа связки диспетчер расписание не видит (раздел 7).
- **Два отдельных входа:** админка записи (servgo.ru/admin, вход через Telegram или подтверждённую почту) и студия
  (growth.servgo.ru, свои логин и пароль из файла аккаунтов). Основа для общего входа уже есть (раздел 7.1).
- **Нет хранилища разговора.**

## 3. Архитектура

```text
Владелец: текст / плашка / голос
      |                         голос: запись -> распознавание (STT) -> текст
      v
Главная growth.servgo.ru  ── подсказки (правила + фоновые идеи)
      |  сообщение с ключом идемпотентности
      v
Диспетчер (отдельный слой, модуль приложения)
  ├─ контекст: профиль + снимок состояния + расписание (этап 5) + факты (этап 6)
  ├─ реестр возможностей: что умеет, последствия, цена, исполнитель, страница
  ├─ решение: ответить / переспросить / выполнить / подтвердить / показать где / «не умею»
  └─ ответ: блоки для экрана + короткая фраза для озвучки
      |                                   |
 сервисы чтения                     Task -> команда (как сейчас)
   + платформа записи (внутренний        |
     метод «кто это», расписание)        |
      |                                   |
      +----- PolicyLayer + Approval (вне промпта) -----+
      v                                                v
 PostgreSQL: разговоры, сообщения, Task, ToolCall, CostRecord, Decision
                                                       |
                       ответ -> озвучка (TTS) -> воспроизведение в браузере
```

Новых сервисов нет (правило 8 из `CLAUDE.md`, на сервере мало памяти): модель, распознавание и озвучка —
внешние API через адаптеры.

### 3.1. Реестр возможностей

Каждое умение описано один раз: описание для диспетчера, параметры, **последствия и цена**, исполнитель,
отображение результата, страница. Диспетчер выбирает только из реестра. Новое умение = новая запись.

Политика определяется не только риском (GREEN/YELLOW/RED из `CLAUDE.md`), но и ценой: дорогое GREEN-действие
тоже требует подтверждения. Иначе случайное нажатие плашки или ослышка в голосе запустит дорогую генерацию.

**Первый реестр (этап 1–2), по решению владельца:**

| Возможность | Класс | Без подтверждения? |
|---|---|---|
| Что в работе, что ждёт решения, показать план / материал / календарь | чтение | да |
| Где это находится / как сделать | чтение | да |
| Создать пост (тема, площадка, аудитория) | GREEN, дешёвое | да |
| Составить или обновить контент-план | GREEN | да (план всё равно утверждается отдельно) |
| Утвердить план | YELLOW | нет — кнопка |
| Рисованное видео | GREEN, дорогое | нет — существующий шаг подтверждения расхода показывается карточкой в ленте |
| Отменить рисованное видео | GREEN | да |
| Утвердить / отправить на доработку материал | YELLOW | нет — кнопка (этап 2) |
| Запланировать публикацию | YELLOW | нет — кнопка (этап 2) |
| Бюджет, цены, доступы, удаление | RED | не выполняется; объяснение и ссылка |

Пакеты статей, креативные видео/сторис/картинки и бизнес-разведка в первый реестр **не входят**, пока не
станут надёжными: на них диспетчер даёт ссылку на страницу и честно говорит, что сам пока не запускает.

### 3.2. Как диспетчер принимает решение

1. Получает сообщение, недавние реплики и контекст.
2. Возвращает структурированное решение по схеме: намерение, возможность, параметры, уверенность, текст для
   экрана, короткая фраза для озвучки, плашки следующего шага.
3. Не хватает параметров или низкая уверенность — один вопрос с вариантами-плашками; не угадывает.
4. Несколько просьб в одном сообщении («план и два поста») — выполняет первую, остальные предлагает
   плашками. Одно действие за ход — проще контроль и отмена.
5. Просьба вне реестра — «этого я пока не умею», ссылка, если есть страница; запрос записывается
   как сигнал спроса (что делать следующим).
6. Нет данных (например, расписание до этапа 5) — прямо говорит, что не видит их. Никаких
   правдоподобных выдумок.
7. Выполняет только то, что разрешает политика; объявляет, что сделал («передаю маркетингу — пишу пост»).

Политика проверяется кодом, а не промптом: даже если модель «решила» выполнить YELLOW-действие, сервер
заменит его карточкой подтверждения.

### 3.3. Блоки ответа

Фиксированные типы: текст, плашки, кнопки-ссылки, таблица, карточка задания, карточка материала, карточка
подтверждения. Плюс отдельное поле «что сказать вслух».

- Цифры и таблицы — из сервисов чтения, а не из текста модели.
- Ссылки собирает сервер по реестру и идентификаторам.
- Невалидные блоки отбрасываются; владелец всегда получает текст и прямую ссылку.
- Внешнее содержимое (исследования, комментарии) — данные; оно не может вызвать действие.
- Таблицы не зачитываются вслух: голосом звучит короткий итог («Три материала ждут проверки — они на экране»).

## 4. Контекст бизнеса

1. Профиль компании (версионируемые файлы и утверждённый профиль).
2. Снимок состояния — компактная сводка, строится кодом.
3. Факты и гипотезы (этап 6). Расписание — этап 5, раздел 7.4.

Через `PrivacyGateway`; без ключей; каждый инструмент изолирован компанией и аккаунтом.

## 5. Подсказки

Клик **сразу отправляет** (решение владельца). Отсюда требования:

- **Каждая плашка — законченный запрос.** Шаблоны вида «Пост на тему…» недопустимы: вместо них конкретные темы
  («Пост: как онлайн-запись снижает неявки»).
- **Плашка несёт готовое намерение.** Для неё не нужен вызов модели на распознавание: ответ быстрее, дешевле и
  предсказуем. Диспетчер подключается, только если нужно уточнение.
- **Темы готовятся заранее** фоновой задачей в воркере из профиля компании и кешируются; не генерируются при
  каждом открытии страницы.
- Случайное нажатие безопасно: без подтверждения выполняются только чтение и дешёвые действия.

Приоритет источников: (1) требует внимания; (2) следующий шаг по ходу разговора — заменяет общие после ответа;
(3) из анализа (этап 6); (4) постоянные и темы. Холодный старт — только (1) и (4). Число плашек — по ширине,
в одну–две строки (решение владельца по интерфейсу).

## 6. Интерфейс и голосовой диалог

### 6.1. Раскладка

Десктоп: как в Google — заголовок, строка с кнопкой микрофона, плашки, ниже лента ответа. Страница без
прокрутки; прокручивается только лента.

Телефон (брендбук ServGo Air): сверху лента, внизу у большого пальца строка, микрофон и плашки (одна строка
с горизонтальной прокруткой), ниже навигация. Всё, что есть на десктопе, доступно на телефоне.

Один разговор с историей; отдельного «режима команд» нет. Голосовой диалог идёт в той же ленте:
реплики владельца показываются расшифровкой, ответы — текстом, блоками и голосом.

### 6.2. Конвейер голоса

Запись в браузере → наш сервер → распознавание → диспетчер (как обычный текст) → короткая фраза → озвучка →
воспроизведение.

Почему не «речь-в-речь» в реальном времени (Realtime API и аналоги): такой поток обходит `PrivacyGateway`,
политику, реестр и блоки и привязывает к одному поставщику. Конвейер медленнее, но сохраняет все правила
платформы. Пересмотреть можно позже, если задержка окажется неприемлемой.

Распознавание и озвучка подключаются через собственные интерфейсы (как `LLMProvider`). Озвучка — на
существующем адаптере OpenRouter, но он настроен под видео (ожидание ответа до 600 с, ограничение длины
фрагмента): для диалога нужны отдельные настройки — короткий тайм-аут и переход на «только текст» при задержке. Провайдер распознавания выбирается тестом на реальных фразах владельца:
качество русского, цена, доступность из России, оплата.

### 6.3. Очерёдность реплик

- **Первая версия — «нажал-говоришь»:** нажать микрофон, говорить, нажать ещё раз. В салоне шумно,
  автоматическое определение конца фразы будет срабатывать ложно. Режим «без рук» — после теста.
- **Перебивание:** нажатие на микрофон во время ответа останавливает воспроизведение и начинает запись.
- **Подтверждения голосом (решение владельца — разрешены):** голосовое «да» подтверждает карточку так же, как
  кнопка. Защита от ослышки:
  - перед вопросом диспетчер вслух называет, что именно произойдёт и что это платно / необратимо
    («Запускаю рисованное видео „Как снизить неявки“, это платная генерация. Подтверждаете?»);
  - «да» относится только к последней неотвеченной карточке и ни к чему другому;
  - подтверждением считается только однозначный короткий ответ («да», «подтверждаю», «запускай»); «да, но…»,
    сомнение или низкая уверенность распознавания — диспетчер переспрашивает;
  - подтверждение записывается в `Approval` со способом «голос» и расшифровкой фразы;
  - RED-действия голосом не подтверждаются никогда.
- **Нет микрофона или отказ в доступе** — остаётся текст, с понятной подсказкой.

### 6.4. Задержка

Ход = распознавание + модель + озвучка, без потоковой выдачи. Чтобы диалог не «молчал»:

- мгновенная реакция интерфейса (звук и анимация «слушаю / думаю»);
- быстрая модель на роли диспетчера, короткий контекст, короткая фраза для озвучки;
- долгие задания не ждём: «Запустил пост, напишу, когда будет готов» + карточка;
- задержки распознавания, модели и озвучки измеряются отдельно (есть страница скорости моделей);
  целевое время ответа определяем по замерам вместе с владельцем.

### 6.5. Браузеры

- iOS Safari пишет звук в mp4/AAC, Chrome — в webm/Opus: сервер принимает оба формата.
- Воспроизведение звука на iOS разрешено только после действия пользователя — схема «нажал-говоришь» это
  выполняет.
- Микрофон работает только по HTTPS (growth.servgo.ru — HTTPS).

## 7. Связка с платформой записи

Цель: владелец бизнеса один раз входит в ServGo и попадает в студию без второго логина, а диспетчер видит его
расписание. Обе части — в двух репозиториях: `booking_bot` (платформа записи) и `Ai_growth_os` (студия).

### 7.1. Что уже есть (проверено в коде 22.10.2026)

- **Общая сессия ServGo.** Платформа записи выдаёт куку `servgo_session` на весь домен `.servgo.ru` и хранит
  сессии в отдельной базе `servgo_auth` (`servgo_auth.py`, поле `source_service` уже заложено под несколько
  сервисов). Так как growth.servgo.ru — поддомен, кука **уже доходит** до студии; студия её пока не читает.
- **Кто владелец:** `Business.owner_id` и таблица совладельцев `BusinessOwner` (роли owner / co_owner);
  сотрудники `Employee` с ролями master / administrator. Пользователь — `User` с Telegram и подтверждённой почтой.
- **Оба приложения на одном сервере:** студия слушает внутренний порт 8091, платформа записи уже обращается к ней
  локально (почта ServGo проверяет логины через студию). Значит, связь делается внутри сервера, без открытия
  новых адресов в интернет.
- **Расписание:** у бизнеса часы работы, перерыв, шаг записи; у записи дата, время, длительность, мастер, услуга,
  статус, цена; выходные мастеров. Свободные слоты уже считает публичный метод `/businesses/{id}/slots`,
  есть аналитика владельца (`/admin/analytics/...`).
- **В студии** вход — логин и пароль из файла аккаунтов с привязкой к компаниям (`studio_product_ids`),
  оператор видит всё.

### 7.2. Общий вход

1. Пользователь вошёл в ServGo (Telegram или почта) — у него есть `servgo_session`.
2. Открывает студию (кнопка «Маркетинг — AI Growth OS» в админке уже есть). Студия видит куку и проверяет её
   **внутренним запросом к платформе записи** («кто это и какими бизнесами он владеет»). Студия не подключается
   к базе входа напрямую и не хранит чужие пароли.
3. Ответ: пользователь и список его бизнесов с ролью. По таблице привязки (7.3) студия получает разрешённые
   компании — те же `studio_product_ids`, что и сейчас, поэтому вся существующая изоляция компаний работает без изменений.
4. Выход из ServGo удаляет общую куку — студия при следующей проверке тоже считает пользователя вышедшим.
   Результат проверки можно кратко кешировать в памяти процесса, чтобы не дёргать платформу на каждый запрос.
5. Нынешний вход по логину и паролю остаётся: им пользуются оператор, API-клиенты и проверка входа в почту ServGo.
   Общий вход — второй способ, а не замена.

Доступ по ролям: владелец и совладелец — полный доступ к своей компании. Администратор и мастер — решение
владельца (раздел 14).

Безопасность: кука должна уходить только по HTTPS — проверить на боевом сервере, что `AUTH_COOKIE_SECURE`
включён (по умолчанию в коде он выключен). Запись в студию по-прежнему защищена проверкой источника
и CSRF. Кука видна всем поддоменам `.servgo.ru` — это осознанный риск общего входа.

### 7.3. Привязка бизнеса к компании студии

- В студии новая таблица привязки: бизнес в платформе записи ↔ компания в студии, кто и когда привязал.
- **Первый вход владельца без компании в студии:** студия предлагает создать компанию, заранее заполнив
  название, тип, адрес и услуги из платформы записи; дальше — существующий сбор данных о компании.
- **Существующие компании** привязывает оператор вручную (страница аккаунтов).
- Один бизнес — одна компания студии; у владельца нескольких бизнесов — несколько компаний и привычный выбор
  компании.

Важная оговорка: компания «ServGo» в студии — это продвижение самой платформы, а не салон с расписанием.
Для проверки подсказок по расписанию нужен **настоящий бизнес** в ServGo (раздел 14).

### 7.4. Чтение расписания

- В платформе записи — **внутренний метод только для чтения** (доступен с того же сервера, по служебному ключу из
  переменной окружения): часы работы, услуги, мастера, выходные, записи за период, свободные окна.
  Свободные окна считаются **существующей** логикой слотов — второго движка расчёта не создаём (правило
  `booking_bot/CLAUDE.md`).
- **Минимум персональных данных:** по умолчанию метод не отдаёт имена и телефоны клиентов — для загрузки
  и пустых окон они не нужны. Если владелец спросит «кто у меня следующий», таблицу с именами показывает сервер
  напрямую из платформы, **минуя модель**, — имена клиентов не уходят внешним провайдерам.
- В студии — адаптер «источник расписания» (интерфейс + реализация для ServGo), чтобы позже подключать другие
  системы записи.
- Снимок для контекста диспетчера: сегодня и неделя — записей, загрузка по дням и мастерам, ближайшие свободные
  окна. Строится кодом, цифры в ответ попадают из адаптера, а не из модели.
- Новые возможности диспетчера (чтение): «сколько записей сегодня / на неделе», «где свободные окна», «загрузка
  по мастерам», «покажи расписание» — ответ таблицей и кнопкой «Открыть расписание» в админке ServGo.
- Действия с записями (перенос, отмена, создание) **не входят**: только чтение.
- Платформа недоступна — диспетчер говорит «сейчас не вижу расписание», остальное работает.

### 7.5. Что это даёт фоновому анализу

Ежедневно воркер студии сохраняет **агрегаты** (загрузка по часам и дням недели, отмены, неявки) — не копию
записей. Сырые данные остаются в платформе записи и читаются при пересчёте, как требуют заметки от 17.10
(верхние уровни опираются на сырые данные). Отсюда подсказки вида «по вторникам после 18:00 пусто — сделать
пост с акцией?».

### 7.6. Выкладка двух репозиториев

- Порядок: сначала метод в платформе записи (без него студии нечего читать), затем студия.
- В `booking_bot` автоматический деплой покрывает только веб-фронтенд и `webapp`; изменения API выкладываются
  отдельным точечным процессом. Перед выкладкой — сверка затронутых файлов с сервером (в `booking_bot/CLAUDE.md`
  зафиксировано, что сервер расходится с GitHub).
- Служебный ключ — в переменных окружения обоих приложений, не в коде и не в логах.

## 8. Данные и аудит

Новые сущности (миграция Alembic):

- **Разговор** — компания + аккаунт (у компании может быть несколько аккаунтов); «новая тема» начинает новый.
- **Сообщение** — роль, текст, способ ввода (текст / плашка / голос), блоки, фраза для озвучки, ссылки на задания,
  модель, ключ идемпотентности, порядковый номер.
- **Ход диспетчера** — решение, возможность, параметры, уверенность.

Связи: действие → `ToolCall`; работа команде → `Task` с пометкой происхождения; каждый вызов модели,
распознавания и озвучки → `CostRecord`; важные рекомендации → `Decision` со ссылками на доказательства
(пустой набор, если их нет); YELLOW и дорогие действия → `Approval`.

## 9. Надёжность

- **Идемпотентность:** браузер присваивает сообщению ключ; повтор при плохом мобильном интернете не создаёт
  второе задание. Задания создаются с `dedupe_key`.
- **Порядок:** в одном разговоре обрабатывается одно сообщение за раз; следующее ждёт. Две вкладки видят одну ленту.
- **Сбой модели:** тайм-аут и запасная модель; если обе не ответили — плашки и прямые ссылки, в голосе —
  «не получилось, попробуйте ещё раз».
- **Сбой распознавания или озвучки:** текст остаётся, диалог продолжается без голоса.
- **Результат, когда владельца нет на странице:** готовое задание появляется в ленте и в существующих
  уведомлениях вкладки. Уведомление в Telegram (бот управления уже есть) — отдельный шаг, не в этапах 1–3.
- **Откат:** переключатель функции на уровне компании; прежняя главная доступна по запасному адресу.
  Сначала включается только для ServGo.
- **Развёртывание:** на сервере студии часть правок делалась вручную и не попала в GitHub — перед выкладкой
  сверить серверные файлы с `main` и выкладывать только перечень изменённых файлов штатным процессом.

## 10. Персональные данные

Голос — персональные данные; отправка записи иностранному провайдеру распознавания может считаться
трансграничной передачей по 152-ФЗ. Для своей компании (ServGo) владелец это **разрешил** (22.10); **до подключения
клиентов** нужна консультация юриста (это не юридическая оценка). Это же касается данных расписания, если
в них попадут персональные данные клиентов (по умолчанию не попадают, раздел 7.4). По умолчанию запись не хранится после
распознавания (раздел 14).

## 11. Как поймём, что работает

Метрики (не ограничения):

- доля запросов, решённых с главной без ручного перехода по меню;
- доля переспросов и доля исправлений владельцем («не то»);
- запросы вне реестра — что добавлять следующим;
- время ответа (p50 / p95) по частям: распознавание, модель, озвучка;
- стоимость хода и стоимость на компанию в день.

Проверка до включения: эталонные фразы → ожидаемая возможность (включая RED, «не умею», «нет данных»,
несколько просьб сразу, ослышки); тесты на фейковом провайдере (схемы, политика, изоляция компаний,
идемпотентность, порядок сообщений, отказы); прогон на живой модели и просмотр владельцем; интерфейс на 390 px
и на десктопе.

## 12. Вне рамок (осознанно)

- Действия с записями (создание, перенос, отмена) — только чтение расписания.
- Диспетчер внутри админки записи: он живёт в студии, админка ведёт в него кнопкой.
- Отмена обычных заданий на контент (нет поддержки в коде; появится вместе с ней).
- Голосовой режим «без рук».

## 13. Этапы

**Этап 0. Опора.** Владелец назвал надёжные функции (план, рисованное видео, посты). По данным заданий за последние
недели сверить долю успешных запусков именно этих трёх; найденные регулярные сбои исправить до запуска диспетчера.

**Этап 1. Текст.** Новая главная: строка, плашки (требует внимания + постоянные + темы из воркера), лента.
Диспетчер с возможностями: чтение и навигация, пост, план, рисованное видео с карточкой подтверждения, отмена
видео, «переспросить», «не умею», «нет данных». Блоки: текст, плашки, ссылки, карточка задания, карточка
подтверждения. Разговор, `ToolCall`, `CostRecord`, роль «диспетчер», переключатель, запасной адрес, только ServGo.

**Этап 2. Богатый ответ.** Таблицы, карточка материала («Утвердить / Доработать»), постановка публикации
с подтверждением, плашки по ходу разговора, возврат результата задания в ленту.

**Этап 3. Голосовой диалог.** Тест провайдеров распознавания, «нажал-говоришь», озвучка ответов через
существующий адаптер, перебивание, оба формата записи, замеры задержки.

**Этап 4. Общий вход и привязка бизнеса** (раздел 7.2–7.3). Не зависит от диспетчера и может идти
параллельно с этапами 1–3: внутренний метод «кто это» в платформе записи, чтение общей куки в студии, таблица
привязки, создание компании при первом входе, проверка флага Secure у куки.

**Этап 5. Расписание в диспетчере** (раздел 7.4). Внутренний метод чтения в платформе записи, адаптер в студии,
снимок для контекста, возможности «записи / окна / загрузка», таблицы без имён клиентов в модели. Пилот на
настоящем бизнесе.

**Этап 6. Знание о бизнесе.** Ежедневные агрегаты, фоновый анализ (день / неделя / две недели / месяц),
гипотезы и факты, подсказки из анализа. Подробности — `OWNER_INTERFACE_AND_INSIGHTS.md`, разделы 4, 5, 7.

**Этап 7. Дальше.** Telegram-уведомления о готовых заданиях, режим «без рук», действия с записями,
новые возможности по сигналам спроса.

Порядок этапов 3 (голос) и 5 (расписание) можно поменять: расписание дешевле и сильнее показывает «диспетчер знает
мой бизнес», голос дороже. Решение владельца — раздел 14.

## 14. Вопросы к владельцу

**Закрыто 22.10:** режим общения — голосовой диалог; плашка отправляет сразу; надёжны план, рисованное видео,
посты; голосовое «да» разрешено; иностранное распознавание для ServGo разрешено; связка с расписанием и общий вход —
в плане.

**Нужно решить:**

1. Кто, кроме владельца и совладельца, входит в студию через общий вход: администраторы бизнеса? мастера?
2. На каком настоящем бизнесе в ServGo пилотировать расписание в диспетчере?
3. Что раньше: голосовой диалог (этап 3) или расписание в диспетчере (этап 5)?
4. Показывать ли модели имена клиентов, если владелец спрашивает про конкретные записи? По плану — нет: таблицу
   с именами отдаёт сервер, минуя модель.

**Ограничения, которые не вводятся без ответа владельца:**

- предельная длина голосовой записи и длина озвучиваемого ответа;
- сколько прошлых реплик передавать модели и сколько хранить разговоры;
- лимит расходов или числа запросов к диспетчеру на компанию;
- хранение аудио (по умолчанию — не хранить после распознавания);
- глубина истории расписания, которую читает диспетчер и фоновый анализ.
