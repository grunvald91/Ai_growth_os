## Один клик вместо ручного ввода ключа сообщества

Новый *условный* сценарий ServGo: ссылка `vk.com/название` → **Подключить ВКонтакте**
→ окно авторизации сообщества на `oauth.vk.com` → проверка прав →
зашифрованное сохранение ключа в нужной компании. Числовой ID, ключ и приложение
VK клиенту вручную искать не нужно. ID короткой ссылки получается через
`groups.getById` с платформенным сервисным ключом или временным app service
key, полученным у VK по `client_credentials`; в адрес VK не передаётся
пользовательский пароль или секрет приложения.

**Важно:** этот поток использует отдельное **классическое VK community OAuth**
приложение, не `VK ID`. Владелец ServGo может один раз внести ID и защищённый ключ приложения на
`/studio/tune/vk` (все значения шифруются существующим интеграционным
хранилищем, секрет не показывается в HTML). Альтернативный источник —
оба параметра окружения `SOCIAL_VK_COMMUNITY_APP_ID` и
`SOCIAL_VK_COMMUNITY_APP_SECRET`, имеющие приоритет над хранилищем;
зарегистрируйте разрешённый HTTPS callback
`https://servgo.ru/studio/social/vk/group-callback` в настройках
данного приложения. VK ID `vk2.a` не является заменой токена сообщества
для `wall.post`. Новые приложения VK могут не поддерживать старый OAuth
вообще. **Совместимость с реальным VK пока не подтверждена; без данных
приложения кнопка не появляется.** После сохранения ID и секрета кнопку
сначала видит **только владелец ServGo**, чтобы проверить настоящий OAuth-
вход на своём сообществе. **Одного успешного входа недостаточно**:
только последующая явно утверждённая публикация, получившая реальный `post_id`
от `wall.post`, сохраняет отпечаток приложения и открывает вход
всем организациям. Тесты с подменённым VK API не засчитываются.
Смена приложения/секрета автоматически снимает отметку о проверке.
Не открывать способ всем компаниям до
успешного живого теста на собственном сообществе. После отказа провайдера
остаётся уже проверяемый ручной способ с ключом сообщества.

Только сервер обменивает code на ключ; callback проверяет подписанное короткоживущее
состояние, исходную организацию, текущего владельца и точный group ID. Ключи
хранятся зашифрованными, а временные ключи с указанным `expires_in` нельзя
использовать после срока действия. Автопубликация без отдельного утверждённого
материала и подтверждения владельца недоступна.

# ServGo Growth Studio — VK ID и публикация на стене

Рабочий PR: [#364](https://github.com/grunvald91/Ai_growth_os/pull/364). Реальная авторизация и внешний вызов `wall.post` ещё **не выполнялись**; до живого теста нельзя считать интеграцию подтверждённой.

## Функциональность

- В `/studio/products/{product_id}/channels` есть ссылка «Управлять VK», ведущая на `/studio/products/{product_id}/vk`.
- Авторизация VK ID идёт через `https://id.vk.ru/authorize` и server-side OAuth 2.1 PKCE (S256), десятиминутное одноразовое состояние в HttpOnly SameSite=Lax cookie. Обратный адрес привязан к canonical ServGo; нельзя подменить организацию.
- В публикациях и на карточке VK комментариев пользователь вставляет обычную ссылку `vk.com/имя`, а после входа VK ID ServGo получает числовой ID сам и проверяет статус редактора/администратора и чтение стены. **Но это не доказывает доступ к `wall.post`**.
- В ноябре 2026 зафиксирована практическая несовместимость токенов типа `vk2.a.*` из нового VK ID с записью на стену (`wall.post`, ошибка 1051); см. https://github.com/gitroomhq/postiz-app/issues/1408 . Подключение VK ID оставлено как проверяемый путь для приложений с надлежащими разрешениями, но без обещания, что публикация заработает.
- **Основной путь текстовых публикаций:** владелец вводит ссылку сообщества и ключ из «Управление → Работа с API». ServGo проверяет право `wall` (бит 8192) и принадлежность ключа указанному сообществу через read-only методы; после этого разрешает создать одно подтверждённое задание. Фактический `wall.post` подтверждается только ответом VK с `post_id`. Ключ сообщества не подходит для `wall.get` / `wall.getComments`. Независимые живые проверки в 2026 году свидетельствуют, что текстовый `wall.post` с ключом сообщества работает, несмотря на ограничение схемы API. Это не гарантирует результат с любым конкретным ключом.
- Очередь принимает только утверждённые `channel_text` материалы с `channel="vk"`. Имеется защита версии и отпечатка, от запрещённой остановленной кампании, редакторских незавершённых задач и повторного назначения поста.
- Отправляются **только текстовые сообщения**, без изображений/видео. `wall.post` от имени нужного сообщества с постоянным `guid` для ID публикации. Успех записывается по реальному `post_id`; сетевая неопределённость превращается в `delivery_unknown`, без автоматического повтора.
- В режиме выключенного worker можно безопасно проверить интерфейс и создание очереди, но новая запись **не выходит** во ВКонтакте.
- Изоляция бизнесов: Studio SSO, Origin/CSRF, `product_id`, владельческая валидация материала, точный ID сообщества. Публикации и настройки разных компаний не смешиваются.

## Конфигурация

В контейнере API и worker:

```env
SOCIAL_VK_CLIENT_ID=<optional_numeric_vk_id_application_id>
SOCIAL_VK_COMMUNITY_APP_ID=<optional_classic_community_oauth_application_id>
SOCIAL_VK_COMMUNITY_APP_SECRET=<optional_classic_community_oauth_secret>
SOCIAL_VK_SERVICE_TOKEN=<optional_read_only_app_service_token>
SOCIAL_VK_REDIRECT_BASE=https://servgo.ru
CONTENT_VK_AUTOPOST_ENABLED=true
CONTENT_VK_MAX_LATENESS_MINUTES=60
```

Владелец ServGo может настроить платформенный сервисный ключ **без доступа к серверу** на `/studio/tune/vk`. Нужно вставить ключ собственного VK-приложения и ссылку на открытое сообщество с постами для проверки. ServGo выполнит read-only запросы `groups.getById`, `wall.get`, `wall.getComments`, после чего сохранит ключ зашифрованным в постоянной интеграционной папке. Ключ не отображается в UI, не передаётся агентам и не попадает в исходники. Страница защищена `require_tune_owner` и CSRF. После настройки в странице VK нужной компании есть кнопка **«Подключить чтение комментариев»**, не требующая повторного ввода её ключа. `SOCIAL_VK_SERVICE_TOKEN` остаётся необязательным альтернативным конфигурационным источником, который имеет приоритет над ключом в хранилище. При отсутствии сервисного ключа текстовые публикации доступны, а чтение комментариев остаётся неподключённым.

Для необязательного способа авторизации через VK ID необходимо зарегистрировать точный redirect URI:

`https://servgo.ru/studio/social/vk/callback`

После подтверждённой read-only проверки 20.11.2026 (нет явного `CONTENT_VK_AUTOPOST_ENABLED` в контейнере и `overlay_env`, очередь VK была пуста) значение по умолчанию для текстовой автопубликации включено в коде. Предохранители по-прежнему требуют подключение сообщества, утверждённый материал, явное подтверждение публикации и допустимое время; посты старше `CONTENT_VK_MAX_LATENESS_MINUTES` (по умолчанию 60 минут) помечаются как неотправленные без вызова VK. Для аварийного отключения установите `CONTENT_VK_AUTOPOST_ENABLED=false` в окружении worker. На новом сообществе сначала проверьте один тестовый текстовый пост.

1. Запустить `python -m pytest -q tests/test_vk_publishing.py tests/test_comments.py tests/test_telegram_publishing.py` в CI. Смотреть результат для **текущего HEAD** PR; прежние зелёные запуски не подтверждают более поздние изменения.
2. Проверить в UI `/studio/products/<product_id>/vk`: анонимный GET/POST, tenant SSO, Origin/CSRF и корректность тёмной темы на Android.
3. При наличии VK ID приложения попробовать вход редактора тестового сообщества. Если VK ID выдаст токен, а `wall.post` откажет с 1051, не отмечать канал как работоспособный для автопубликации.

6. Проверить отказ с чужим product_id и чужим материалом, смену ключа до отправки, дубль `guid`, отмену и отключение. До подтверждённого результата не включать VK для всех клиентов.

## VK фото: подготовка, загрузка и отправка (PR #383)

После подтверждения владельцем `channel_text` с `channel=vk` и
`image_model != none`:

1. `schedule(..., products_root=settings.products_root)` проверяет наличие
   настоящего PNG, SHA-256, связь изображения с текстом, и сохранённый
   `approved` от визуального критика. В `vk_publish_intent` сохраняются
   `image_artifact_id` и `image_sha256`. Без изображения, одобрения или
   доступа к каталогу такой пост **не планируется**.
2. Worker повторно проверяет неизменность текста, изображения, исходных файлов,
   исходного VK-сообщества и прав публикации; фиксирует `sending` ДО
   первого внешнего действия. Если входные данные поменялись, ничего в ВК
   не отправляется.
3. `photos.getWallUploadServer(group_id)` → HTTPS multipart `photo` на
   подтверждённый хост `pu.vk.com` или `pu.vk.ru` → `photos.saveWallPhoto`.
   Используются только реальные `owner_id` и `id` ответа ВК, а не ID
   сообщества, угаданный по шаблону. Контрольная сумма PNG повторно
   проверяется прямо перед multipart.
4. **Только после сохранения фотографии** отправляется `wall.post` с
   `attachments=photo{owner_id}_{id}`, исходным текстом и устойчивым
   `guid=publication_id`. Текст отдельно после ошибки загрузки не отправляется.
   Если загрузка не прошла — `failed_before_send` с описанием в Studio;
   если ответ `wall.post` неизвестен — `delivery_unknown` и только
   ручная сверка стены, без автоматического повторного поста.

### Ограничения реального VK API

VK community-key может позволять `wall.post`, но **отклонять**
`photos.getWallUploadServer` с `error_code=27` даже при выданном
разрешении `photos`. Описание воспроизводимого случая:
https://github.com/VKCOM/vk-api-schema/issues/242 .

Если ранее подключён совместимый **пользовательский ключ классического VK API**
того же сообщества, worker предпочитает его для загрузки фото после проверки
администраторских прав через `groups.getById`. Финальный `wall.post`
по-прежнему идёт через ключ публикации сообщества. Ключ VK ID
`vk2.a` не считаем доказанно пригодным для этих методов; по наблюдениям
он может вызывать ошибку 1051:
https://github.com/gitroomhq/postiz-app/issues/1408 .

**Нет подтверждения реальной публикации с фото на пользовательском сообществе.**
Автоматические тесты перехватывают HTTP на границе ВК, проверяют точную
мультичастную передачу, область доступа, отказ от text-only,
идемпотентность, ошибку загрузки, повреждённый файл и неопределённый
ответ `wall.post`. Никаких реальных токенов или публикаций не запускают.

Если VK API возвращает другой официальный адрес для загрузки, не следует
отключать проверку URL: сначала проверить принадлежность нового домена ВК,
а затем расширить доверенный список в коде и тестах.

## Ревью официального протокола публикации фотографий (23.11.2026, PR #409)

Первоисточники: [официальная схема VK API v5.199 — photos](https://github.com/VKCOM/vk-api-schema/blob/master/photos/methods.json), [официальная схема wall.post](https://github.com/VKCOM/vk-api-schema/blob/master/wall/methods.json), [VK Java SDK: пример загрузки и публикации фото](https://github.com/VKCOM/vk-java-sdk#request-sample-for-uploading-and-posting-photos-on-user-wall), [официальный VK Android SDK: VKWallPostCommand](https://github.com/VKCOM/vk-android-sdk/blob/master/samples/app/src/main/java/com/vk/sdk/sample/requests/VKWallPostCommand.kt). [Отчёт об ошибке 27 на ключе сообщества (03.04.2026)](https://github.com/VKCOM/vk-api-schema/issues/242) — опыт разработчика, **не** официальная гарантия поведения всех VK-ключей.

Проверенный по первоисточникам порядок:
1. Пользовательский VK API ключ с правами на группу и фото вызывает `photos.getWallUploadServer(group_id=POSITIVE_GROUP_ID)` и получает временный `upload_url`.
2. Отправляет PNG/JPEG на именно этот HTTPS `upload_url`: `POST multipart/form-data`, поле **`photo`**, без API-ключа в URL или multipart заголовках.
3. Использует `photos.saveWallPhoto(group_id=POSITIVE_GROUP_ID, server, photo, hash)`, где `server/photo/hash` возвращены загрузчиком. Официальный SDK читает `server` как числовую строку, тогда как схема метода сохранения использует целое число. ServGo нормализует оба варианта и запрещает нечисловые.
4. Получает `owner_id` / `id` сохранённого фото, проверяет принадлежность нужному сообществу и передаёт `attachments=photo<owner_id>_<id>` в `wall.post(owner_id=-POSITIVE_GROUP_ID, from_group=1, message=..., guid=...)`. `guid` — устойчивый идентификатор попытки; при неясном ответе `wall.post` повтор не выполняется.

**Разграничение ключей:** официальная схема VK API 5.199 для `photos.getWallUploadServer`, `photos.saveWallPhoto` и `wall.post` указывает `access_token_type=user`. При этом в существующих практических тестах ServGo ключ сообщества допускался для текстового `wall.post`; это отклонение от схемы не является гарантией доступа для фото. VK ID-токен `vk2.a.*` нельзя считать доказанно совместимым с классическим методом загрузки стены. Для фото предпочтителен **отдельный проверенный пользовательский ключ**.

В Studio VK добавлен отдельный раздел **«Фото: настроить доступ к загрузке»**, не заменяющий ключ сообщества для текста и комментариев. При сохранении пользовательского ключа ServGo проверяет `groups.getById` с признаком администратора именно подключённой группы, вызывает `photos.getWallUploadServer` без передачи файла, проверяет официальный HTTPS адрес, сохраняет ключ зашифрованно. Он используется только для этой организации и её группы, при публикации фото — и для финального `wall.post`, согласно формальной схеме VK API. Старые пользовательские ключи отзываются локально при замене; при полном отключении VK удаляется и ключ для фотографий.

**Ограничения проверки:** получение адреса `upload_url` не равно успешной загрузке фото и не гарантирует успешный `wall.post`. Полный сценарий проверен в CI только на имитированном VK API; реальный подключённый VK и конкретное фото становятся подтверждёнными только после фактической публикации и `post_id`. При отказе до `wall.post` текст без фото не публикуется. Никаких самовольных живых публикаций для проверки эта реализация не делает.

Получать пользовательский ключ следует только через собственное легитимное приложение VK и официальную авторизацию; не вставлять пароль ВКонтакте или ключ в сторонние сайты для получения токенов. Если действующий пользовательский OAuth вашего VK-приложения недоступен, работоспособность автоматической загрузки фотографий **не подтверждена** и не должна маскироваться статусом «VK подключён».

В частности, ключ **не** берётся в `Управление сообществом → Работа с API`: там создаётся ключ сообщества, пригодность которого для `photos.getWallUploadServer` не подтверждена.

Пользовательский ключ сохраняется **один раз** зашифрованно и используется ServGo в следующих публикациях, пока VK сохраняет его действительность и необходимые разрешения. Нельзя обещать вечную работу пользовательского access_token: при истечении срока или отзыве доступа потребуется новое получение ключа (в частности, для краткоживущих VK ID OAuth токенов нужен корректно настроенный refresh, а совместимость с классическими методами API должна быть подтверждена отдельно). Повторное подключение не должно требоваться для каждой публикации **пока сохранённый ключ действителен**. Пароль пользователя, client_secret и ключи доступа никогда не отображаются в HTML или в ссылках.
