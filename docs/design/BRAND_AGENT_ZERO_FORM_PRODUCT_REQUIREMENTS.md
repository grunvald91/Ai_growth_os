# ServGo Brand Agent — фирменный стиль без форм
## Замена ручной настройки на агента с одним полем ввода · PRD v1

**Дата:** 2026-11-04
**Статус:** дизайн-проект; код нового агента ещё не реализован.
**Основа:** уже внедрённые Brand Kit A–E, PR #264, #266, #267.

### 1. Правило продукта

Обычный владелец не должен заполнять десятки цветов, шрифтов и настроек. Он вставляет ссылку на сайт, прикладывает PDF/изображения или говорит голосом «Сделай стиль на основе этого», а агент самостоятельно проводит исследование, извлекает оригинальные фирменные ресурсы, создаёт согласованную палитру и 3 Stories-превью, затем показывает готовый вариант на утверждение.

**Единственное обязательное действие владельца — подтвердить итог либо коротко поправить его в том же чате.** Ручные настройки доступны лишь внутри скрытого «Дополнительно», не как главная страница.

### 2. Один экран — один диалог

Вверху компактный заголовок «Фирменный стиль», название активной компании и статус. Ниже: история сообщений, индикатор этапа работы, миниатюры источников, 3 предпросмотра Stories, заметки об уверенности найденных ресурсов. Внизу — **закреплённая компактная строка**:

- Слева «+» для URL, одного/нескольких PDF, изображений, брендбука, логотипа, скриншотов; показывать прикреплённые миниатюры и удаление до отправки.
- В центре текстовый ввод с естественным языком: «Возьми стиль с моего сайта», «Логотип справа», «Добавь воздуха», «Сделай спокойнее».
- Справа кнопки микрофона и отправки; удерживание микрофона записывает голос, отпускание прекращает; распознанный текст доступен для исправления перед отправкой.
- История остаётся видимой при открытой клавиатуре, не перекрывается панелью и системными жестами. Работает PWA, светлая/тёмная темы.
- На старте достаточно одной строки и вариантов «Вставить сайт / Загрузить брендбук / Прикрепить фото». Нет списка цветов и шрифтов.

Пример переписки: клиент присылает «https://example.com + brand.pdf». Агент: «Изучаю сайт и PDF», затем «Логотип взят из вашего PDF; нашёл 4 фирменных цвета, шрифт определён, 2 изображения использованы как примеры. Подготовил 3 Story-макета». Показывает карточку с превью, ссылками на источники и кнопками **«Применить» / «Изменить словами или голосом»**. Если логотип не подтверждён, один короткий уточняющий вопрос с вариантами. Никаких ложных статусов готовности.

### 3. Источники и достоверность

| Источник | Что собирать | Достоверность |
|---|---|---|
| Сайт компании | Реальные загруженные brand/logo assets, CSS-цвета, web fonts, spacing, shape, изображения, стилизация | Привязать к собственному домену, исходным URL и hash; favicon не называть оригинальным логотипом без проверки |
| PDF / брендбук | Встроенные логотипы, векторные ресурсы, указанные шрифты, таблицы цветов, типовые композиции, бренд-запреты | Использовать встроенные данные/растеризацию и мультимодальный анализ, сохранять документ + номер страницы |
| Фото / PNG / JPG / WebP | Распределение цветов, композиция, декоративные элементы, пример читаемости и визуальный тон | Кандидатные цвета и образцы, но не «точный» оригинал логотипа из обрезанного скриншота |
| Логотип | Оригинальные байты, прозрачность, отношение сторон, варианты светлый/тёмный, контроль целостности | Исходный файл, не подделывать ИИ |
| Текст и голос | Предпочтения и правки пользователя в текущем контексте компании | Явные команды имеют приоритет; не объявлять правки «утверждёнными» автоматически |
| Подтверждённый профиль компании | Название, аудитория, позиционирование | Использовать для содержимого, не заменять визуальный Brand Kit |

Порядок доверия: утверждённый фирменный стиль → загруженные владельцем оригиналы → подтверждённые фирменные ресурсы своего сайта → PDF брендбук → другие примеры → предложения нейросети. Для каждого поля сохранять source_ref, confidence и статус verified/proposed/unavailable.

Шрифты по скриншоту — **похожие**, а не подтверждённые; при неизвестной лицензии использовать разрешённый шрифт с кириллицей. Восстанавливать точный логотип из скриншота запрещено — можно лишь предложить кандидата, который владелец подтверждает; отсутствие оригинала не скрывать.

### 4. Автоматический процесс агента

1. Принять сообщение, URL, вложения и/или распознанную речь, показать статус принятия. Поддержать объединение источников в одном запросе.
2. Создать company-scoped долгоживущую сессию, job ID, журнал источников и чекпойнты, идемпотентный ключ запроса.
3. Безопасно прочитать сайт, PDF, изображения; выделить реальные логотипы, визуальные токены, фотографии, шрифты. При частичной ошибке продолжать обработку доступного, но показать ограничения.
4. Вызвать vision/LLM только для задач, требующих визуального распознавания и интерпретации, с ограничением размера/стоимости и строгой JSON-schema. Для ясных CSS/metadata данных платная модель не нужна.
5. Разрешить противоречия между материалами по иерархии доверия. Создать typеd BrandStyle с доказательствами и пометками uncertain. **Никакого автоматического approve.**
6. Сохранить новую draft-версию в действующем Brand Kit и отрендерить три фирменных примера через имеющийся deterministic renderer **без платной генерации картинок**.
7. Показать владельцу крупные визуальные превью и компактное описание — не HEX-таблицу. При необходимости задать максимум один осмысленный вопрос за ход диалога.
8. На фразу «сделай ярче/логотип левее/без красного» создать изменение draft, отрендерить ещё раз локально, сохранить revision и историю.
9. Только по явной кнопке «Применить» и проверке версии/прав вызвать existing approve_version. Закреплять Brand Kit за новыми Stories. Публикация ничего не запускает.

### 5. Архитектура: использовать существующее

**Не писать второго большого Company Intake и второго STT:**
- Веб-сайты: app/intake/sources.py:PublicWebsiteFetcher (проверка DNS/IP/redirect для SSRF). Дополнить безопасным извлечением CSS/logo/fonts и изображений.
- PDF/OCR: app/intake/file_extract.py и parse_file_async, а для визуальных элементов отдельный рендер PDF-страниц/embedded-image extraction. OCR сам по себе не определяет стиль.
- Vision: проверенный мультимодальный паттерн ClaudeHubChat из app/content/whiteboard/adapters.py. Подключить структурированное извлечение с собственным контрактом для цветов, fonts, logo-candidates, visual_style, layouts, evidence. Не путать vision analysis с платной image generation.
- Voice: уже существующие POST /studio/voice/dictate и MediaRecorder/VoiceGlow. Повторно использовать их логику и авторизацию, не создавать новый STT, не сохранять аудио без необходимости.
- Сохранение: app/brand_kit/service.py:store_asset/save_draft/approve_version, схемы BrandStyle, версии BrandVersion, официальный deterministic renderer из app/brand_kit/renderer.py.
- Уровень доступа: product_id, авторизованный SSO-владелец или делегированный approver. Защищённые URL к ресурсам, multipart limits, file type validation.

Новые компоненты (имена проектные): app/brand_kit/agent/contracts.py, source_collector.py, vision.py, orchestrator.py, chat_service.py; API app/api/brand_agent.py; небольшой frontend JS+CSS для composer, attachment-preview и сообщений; таблицы brand_agent_sessions/messages/sources/jobs (или аналогичная персистентная модель).

Все дорогие и длительные операции выполняются асинхронно воркером/очередью, не в HTTP request и не в памяти процесса. Идемпотентность, статус running/failed/ready, сохранение частичных источников, явное восстановление без повторного списания.

### 6. Контракт API (проект, ещё не создан)

- GET /studio/products/{product_id}/brand-agent — полноэкранная страница, поддержка мобильного web/PWA.
- GET /studio/products/{product_id}/brand-agent/state — лента, текущий job, draft, источники и превью.
- POST /studio/products/{product_id}/brand-agent/files — загрузить материалы, сохранить source id; не делать несанкционированных платных запросов.
- POST /studio/products/{product_id}/brand-agent/messages — текст/URL и source ids → создать/продолжить задачу.
- POST /studio/products/{product_id}/brand-agent/revise — ревизия draft из естественной фразы.
- POST /studio/products/{product_id}/brand-agent/approve — однократное подтверждение конкретной версии с version guard.
- GET /studio/products/{product_id}/brand-agent/updates — прогресс (polling или SSE).
- POST /studio/voice/dictate — существующий endpoint.

### 7. Что не должно происходить

- Никаких обязательных форм, выбора цветовых HEX или десятка позиций.
- Нельзя называть «настоящим логотипом» генерацию ИИ или скриншотный crop без верификации.
- Нельзя объявлять точное совпадение шрифта без проверяемого источника или лицензии.
- Нельзя автоматически утверждать стиль, менять действующую версию, публиковать посты или запускать дорогую генерацию без действия пользователя.
- Нельзя делать новый платный image/API вызов при правке оформленного макета.
- Нельзя переносить бренд/контекст одной компании в другую.
- Нельзя зависать с неподвижным UI без прогресса и возможности продолжить.
- Старую многостраничную форму оставить только под «Расширенные настройки»/rollback, не показывать как основной путь.

### 8. Этапы и definition of done

**BA-01 — UI:** единый чат снизу, прикрепление документов/изображений/сайта, диктовка, история, превью, компактная мобильная верстка; ручные настройки в скрытой секции.

**BA-02 — Durable collection:** company scoped sessions/sources/jobs, безопасное извлечение PDF и website, очередь и прогресс; тесты tenant, лимитов, SSRF, отмены и повторов.

**BA-03 — Visual agent:** мультимодальный разбор и структурная валидируемая extraction; provenance per field; тестовые брендбуки и разные типы картинок; проверка «не подделывать оригинал».

**BA-04 — Draft + chat correction:** автосоздание BrandStyle draft, трёх локальных превью, корректировки по тексту/голосу, no extra image API, версия/аудит.

**BA-05 — Approval + rollout:** одна явная кнопка утверждения, E2E URL-only/PDF-only/image-only/mixed/voice, Android и iPhone, светлая/тёмная тема, canary компании и feature flag, rollback.

**Готовность:** реальный владелец заходит в профиль, отправляет **один сайт или PDF**, получает **три согласованных макета с проверенным логотипом**, при необходимости голосом правит и одной кнопкой утверждает. Если доказанного логотипа нет, агент прозрачно сообщает это. До завершения полного E2E нельзя считать новый поток работающим в production.
