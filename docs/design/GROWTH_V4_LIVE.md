# Рабочее переключение дизайна Growth OS

Старые страницы получают кнопку «Новый дизайн». Она устанавливает предпочтение `growth_design=v4` и сохраняет текущий URL и параметры. В новом интерфейсе есть обратная кнопка «Старый дизайн». Предпочтение хранится в HttpOnly SameSite=Lax cookie; при HTTPS — Secure. По умолчанию остаётся прежний дизайн. Переход через выбор компании и редиректы также сохраняет предпочтение.

## Реальные функции

Рабочий документ собирается из CSS, структуры, SVG и компонентов `growth_os_v4_preview.html`. Демонстрационный JavaScript отсекается полностью. Главная использует композицию v4: приветствие, свободное пространство, командная строка с микрофоном и подсказки. Реальные сообщения, подтверждения и голос обслуживает прежний dispatcher.js.

Создание использует карточки формата v4 и рабочие поля. Доска заданий и библиотека загружают записи компании через `/studio/products/{id}/v4/data`; технические артефакты исключены. Карточки показывают последние 200 записей, полный список с серверными фильтрами доступен ниже. При ошибке загрузки исходный список остаётся доступен. SEO показывает этапы v4 и реальные отчёты. Формы остальных разделов размещаются в структуре v4 с сохранением контролов. Исходные формы, имена полей, DOM-цели, скрипты, обработчики, проверки авторизации и CSRF сохраняются. Реальные диспетчер, подтверждения, обновления задач и голос используют прежние API. Формы с ошибками 422 и ответы после сохранения также сохраняют выбранный дизайн.

Все инструменты доступны через боковую навигацию и мобильное «Ещё»: создание, задания, согласование, материалы, планы, календарь, видео, каналы, аналитика, комментарии, разведка, профиль, аккаунты, модели и настройки агентов. Доступ к административным разделам определяется прежними проверками backend.

Добавлены страницы:

- `/studio/products/{id}/seo`: реальные семантические ядра, SEO-планы и отчёты выбранной компании. Запуск через диспетчер; ссылка заполняет команду, отправку делает пользователь. Внешние запросы и расходы не запускаются при открытии страницы.
- `/studio/products/{id}/campaigns`: реальные маркетинговые эксперименты, каналы и бюджеты. Планирование через диспетчер, контент-планы через действующую форму, почтовые кампании — через ServGo Mail.

Почта открывает рабочий модуль `https://servgo.ru/mail` с его собственным входом и полномочиями. Это не новая копия SMTP-модуля. Новая оболочка использует существующие рабочие формы разделов; отдельный демо-макет `/studio/design-preview` остаётся инструментом дизайна, его демонстрационные кнопки не включаются в production UI.

Неизвестные суммы не отображаются как нулевые. В SEO показываются только записи выбранной компании, технические checkpoint/attempt-артефакты не выводятся. SVG ServGo скопирован в исходный v4 из канонического SVG без изменений и используется в рабочем документе, фирменные цвета логотипа отделены от темы интерфейса.

## Проверки

```bash
python -m pytest -q
python -m pip install playwright
python -m playwright install chromium
python scripts/check_growth_live.py
# Или: python scripts/check_growth_live.py --browser /usr/bin/chromium
```

Браузерный тест запускает локальное приложение с отдельной SQLite-базой, создаёт задачу, вызывает детерминированную команду рабочего диспетчера, проверяет 32 страницы/размера и три общих раздела, тему и переключатели. Внешние модели, отправка почты и публикации не вызываются.

Pytest проверяет переключение, сохранение query, cookies и исходных форм, ошибки валидации, создание задачи, CSRF, запрет анонимного доступа и изоляцию компаний. Дополнительно проверяются отсутствие демонстрационного JS в рабочем документе, отсутствие чужих/технических записей в карточках, мобильное «Ещё», реальная карточка созданного задания и отсутствие горизонтального переполнения.

## Выкладка и откат

Использовать существующий `deploy-growth.yml` с точным commit SHA. Новые зависимости и миграции не требуются. Деплой сначала выполняет полный pytest, затем проверяет расхождения с сервером, активные задания, здоровье приложения и выполняет откат при ошибке.

После выкладки проверить вход, переключение в обе стороны, создание задания, доступ к материалам и сохранение компании в контексте. Старая версия доступна по кнопке «Старый дизайн» без серверного отката; полный откат — штатным `deploy_growth.py rollback`.


## Исправления функционального соответствия

Библиотека v4 использует исходный серверный запрос: kind (включая creative), q, page,24 записи на страницу. Карточки v4 оформляют отфильтрованный результат; отдельная загрузка последних200 материалов больше не подменяет поиск. Доска заданий сохраняет прежний дополнительный подробный список.

В шапке обеих версий экрана находится реальный виджет уведомлений с activity.json, счётчиком и notifications/read-all. Вложенные страницы /studio/tune сохраняют вкладки.

Форма /studio/products/{id}/campaigns/new создаёт Experiment через ExperimentService и валидацию ExperimentCreate. Сохраняется только draft; запуск публикаций/расходов не выполняется. Ошибки422 и дубли409 возвращаются в интерфейсе v4. Полный редактор жизненного цикла кампании пока не реализован.

Почтовые API booking_bot требуют mail_owner и отдельную owner-mail сессию. Встраивание полного почтового интерфейса в Growth требует согласованной серверной интеграции полномочий; текущий переход в ServGo Mail сохраняется. Нельзя считать его переносом почтовых экранов макета.


## Этап Growth V4 — редактирование кампаний (01.11.2026)

Из списка кампаний открывается карточка реального эксперимента выбранной компании
с полями, статусом и записанным итогом. Новая форма редактирует только draft,
использует существующие валидатор ExperimentCreate и ExperimentService, сохраняет
дополнительные сигналы и цель эксперимента. Запущенные кампании доступны только
для просмотра; изменение статуса должно опираться на реальное управление worker,
а не просто на переключение колонки status.

На чтении и записи применяется пара product_id + experiment_id, ошибки другого
бизнеса возвращают 404; недопустимые поля — 422, дубли ключа — 409. Данные HTML
экранируются. Создание и редактирование не запускают платную модель, публикацию,
почтовую рассылку или задания. Изменения ожидают review и release;
развёртывание на сервере этим этапом не выполняется.


## Этап Growth V4 — запуск кампании (01.11.2026)

В карточке черновика доступен POST `/studio/products/{product_id}/campaigns/{experiment_id}/launch`.
Он использует существующий `ExperimentLaunchService.launch` (тот же путь, что Telegram),
а не отдельную реализацию смены статуса. Сервис атомарно блокирует строку Experiment
через `SELECT ... FOR UPDATE` в PostgreSQL, фильтрует `product_id`, проверяет
обязательные поля и состояние `draft`, записывает `running`, даты наблюдения,
решение, импортирует доступный cohort и ставит внутреннюю задачу в очередь.
Второй запуск не создаёт ещё одну задачу (409). Ошибки отсутствующего/чужого
эксперимента возвращают 404; неполный контракт — 409 с сообщением в V4.

Любое изменение требует действующей Studio-авторизации и origin/CSRF проверки,
как и прочие POST. Общие задания не наследуют персональные исключения кампании
EXP-SERVGO-001. Запуск **не отправляет** письма и **не публикует** материалы напрямую,
но очередь research_pmm может потреблять бюджет вызовов ИИ-моделей.
Права бизнесов определяет Studio Auth, а на уровне операции дополнительно
проверяется связка product_id / experiment_id.

Безопасная `stop/finalize` операция в backend не обнаружена. Колонка
`Experiment.status` сама по себе не отменяет запущенные задания, не отзывает
ожидающие одобрения материалы и не останавливает отправку, зарезервированную
до смены статуса. Поэтому кнопки «Остановить» и «Завершить» пока не подключены.
Для реализации потребуются явные переходы состояний, координация с воркерами,
учёт in-flight отправок и проверка изоляции компании.

Регрессии: `tests/test_growth_live.py` (изолированный запуск, отсутствие
публикации/рассылок при POST, повторный запрос, неполные поля, чужая компания,
company-account access и CSRF). PR не выполняет production deploy.


## Обязательное правило интерфейса маркетинговых кампаний

**Одна компания ServGo → собственные маркетинговые кампании → цели, действия,
запрашиваемые решения владельца и измеримые результаты.** На основном экране
кампании владелец должен за несколько секунд понять:

1. **Зачем** кампания: что хотим улучшить.
2. **Что сделает ServGo**: конкретные действия, а не имена агентов/очередей.
3. **Что проверяем**: гипотеза простым языком.
4. **Какой результат нужен и как измерим**: критерий успеха, не обещание гарантии.
5. **Что требуется от владельца сейчас**: одно понятное следующее действие
   либо честное указание, что конкретный запрос на действие отсутствует.

Обязательные согласования **не добавлять без необходимости**: если автоматическое
выполнение разрешено, не требовать ручного утверждения каждого материала.
Если требуется подключение аккаунта, бюджет или просмотр материала, показывать
это только на основании проверенного состояния соответствующего интеграционного
модуля. Не писать «подключено», «согласовано», «запущена реклама», «получено N
клиентов» без реальных данных. Платный рекламный запуск не равен запуску
внутренней ИИ-подготовки.

Основная карточка должна оставаться короткой; технические поля (ключи EXP-,
источники данных, сроки и ограничения эксперимента) доступны по запросу в
«Подробнее». Отображение должно работать в мобильном интерфейсе. Все запросы
к данным — строго внутри `product_id`; показатели кампании фильтровать
дополнительно по `experiment_id`.

**Состояние реализации 01.11.2026:** список и карточка показывают цель,
план действий, критерий успеха, способ измерения, следующий шаг и реальные
показатели `Metric` данной организации. Черновик даёт заполнить недостающие
условия либо инициировать только внутреннюю подготовку; запущенная подготовка
ссылается на настоящие страницы заданий, подключений и проверки. Отсутствующие
показатели не маскируются нулём или обещанием. Технические условия скрыты в
раскрываемой секции.

**Ещё не реализовано:** автоматическое определение требуемого владельцем
подключения для конкретной кампании, привязка согласований/контента к ней,
объективная оценка эффективности (сравнение с базовой линией, атрибуция,
вывод об успехе), worker-safe pause/stop/finalize. До появления связей в
backend не выводить фиктивные «подключить»/«согласовать» как будто система
установила необходимость. Никакой автопубликации, массовых рассылок, платных
запусков и продакшен-деплоя этот этап не выполняет.


## Growth V4 — реальные ресурсы кампании, этап 01.11.2026

На экране кампании показываются только её фактические связи с каналами и
материалами. Для `channel="telegram"` отображается состояние ранее проверенного
Telegram-канала данной организации; владелец может выбрать конкретный
проверенный канал, не предоставляя права заново. Если такого канала нет,
предлагается перейти в существующий раздел подключения. Для других
неподтверждённых названий каналов система не выдумывает интеграции.

Материалы связываются с кампанией явно через защищённый POST; дополнительно
подхватываются реальные выходные материалы её подготовительного задания,
если подтверждён совпадающий `task_brief.experiment_id` и `task_id`.
У материала со статусом `awaiting_approval` появляется конкретное действие
«Посмотреть материал» со ссылкой на действующую страницу проверки.
У прочих материалов обязательное согласование **не создаётся**.
Статусы материала берутся из `Artifact.status`, а не из текста контент-плана.

Хранение привязок — служебный `Artifact(kind="campaign_workspace")`,
обновляемый под блокировкой строки `Experiment`; новых таблиц и миграций нет.
Список кампаний загружает связанный контекст пакетно, не делая N запросов
для N карточек. Чтение и изменения проверяют `product_id`,
`experiment_id`, `artifact_id` и тип связанного ресурса. Повторное
добавление материала не дублирует связь. Исторически проверенный Telegram
не объявляется гарантированно доступным в данный момент.

Этот этап **не запускает** внешнюю отправку, публикации, рекламный бюджет,
автоматическое согласование, изменение политики публикации или worker-stop.
Пока поддержана только действующая интеграция проверенных Telegram-каналов.
Остальные подключения должны получить отдельные реестры состояния и
привязки по мере подключения их реальных API. Сопоставление затрат/выручки
с целью и безопасное завершение кампании остаются следующими задачами.


## Growth V4 — измерение эффективности, этап 01.11.2026

Существующая модель `Metric` уже связывает числовые показатели с кампанией и
организацией. Для **сравнения** нужны два измерения основного показателя,
явно помеченные как `baseline` («до») и `result` («после»), с
сопоставимыми единицами измерения и неубывающими датами. При наличии пары
выводится абсолютная разница и процентная относительно ненулевой базы.
Нулевой базовый показатель позволяет рассчитать абсолютный прирост, но не
процент. Отсутствие данных, несоответствие единиц или дат отображаются
как «недостаточно данных», **не как нулевой результат**.

Историческое свободное поле `baseline_summary` и `success_condition`
не подвергаются неявному численному парсингу. Факт роста не доказывает, что
он обусловлен именно этой кампанией; автоматически не присваивать оценки
успешности, окупаемости или выручки без проверенных источников и атрибуции.
Существующие измерения `Metric` сохраняются без изменений.

Дополнительно есть **необязательный** ручной ввод измерений через
`POST /studio/products/{product_id}/campaigns/{experiment_id}/measurements`.
Владелец указывает период «до/после», число, единицу, дату и источник;
данные получают `dimensions.entry_method=owner_manual`, время внесения и
маркировку «источник не проверен автоматически». Ввод не создаёт никаких
задач, рассылок, публикаций и решений о завершении. Данные и методы
ограничены `product_id + experiment_id`, POST защищён Studio Auth/CSRF.
История хранится как отдельные записи, без перезаписи прежних значений.

### Интеграции площадок — отложены

Без обязательного подключения Instagram и YouTube. ServGo может готовить
контент, обложки, подписи, планы и выдавать готовые материалы для ручной
публикации. На этом этапе **не** вводить новые OAuth-потоки, токены клиентов
или обещания автоматической отправки. Instagram API и YouTube Data API
позволяют публикацию при наличии надлежащего типа аккаунта и разрешений,
но для многопользовательского SaaS нужны завершённая регистрация приложения,
проверка прав и защищённое хранение/обновление токенов. VK также отложить
до отдельной практической проверки доступа конкретного бизнеса.

Официальные сведения:
- Meta Instagram API: https://www.postman.com/meta/instagram/collection/6yqw8pt/instagram-api
- Google YouTube OAuth: https://developers.google.com/youtube/data/guides/auth/server-side-web-apps
- VK ID SDK: https://vkcom.github.io/vkid-web-sdk/docs/

**Дальше**: фактическая автоматическая подача измерений из подключённых
источников, проверка атрибуции, worker-safe остановка/завершение по #198.


## Growth V4 — управляемая остановка и завершение кампаний (01.11.2026)

**Не путать остановку маркетинговой кампании и завершение одного задания.**
Команда владельца обрабатывается сервером для пары
`(product_id, experiment_id)`, под транзакционной блокировкой строки
`Experiment`. Повтор одной и той же команды идемпотентен. В
`campaign_lifecycle_event` записываются действие, время, инициатор и
необязательный комментарий. Условия успешности не выводятся автоматически
из текста гипотезы и не превращаются в фиктивные решения KEEP/SCALE.

**«Запросить остановку»** меняет `running → stopping`, отменяет ещё не
начатые связанные задания (по проверенному
`task_brief.experiment_id` и дочерним заданиям), блокирует создание
новой подготовки и отправок из остановленной кампании. Если нет активных
операций, происходит `stopping → stopped` немедленно. Уже выполняющийся
ИИ-расчёт может закончить текущую задачу; не заявлять о его моментальном
прерывании. Пока он не завершился, статус остаётся «Останавливается».
Воркер периодически сверяет состояние и завершает переход только по
реальным фактам.

**«Завершить кампанию»** меняет `running → finishing` и только после
фактического окончания активных операций — `completed`. Владелец
может записать итог своими словами; он помечается как собственный вывод.
При отсутствии сопоставимых измерений экран показывает «Недостаточно
данных». Автоматическая оценка эффективности или причинно-следственной
атрибуции не подменяет решение владельца.

Перед созданием записи `sending` для SMTP проверяется статус
`Experiment` под той же блокировкой, что и запрос остановки. Входящие
команды не аннулируют физически уже начатую сетевую отправку. Для
`ToolCall.status= sending / delivery_unknown` переход в финальный
статус остаётся заблокированным, пока факт отправки не выяснен.

Для **явно привязанных к кампании** материалов календарь Telegram
не допускает нового назначения после запроса остановки, а
планировщик отменяет ещё не отправленный пост до создания долговременного
send lease. Если сетевое обращение уже началось, переход блокируется до
уточнения результата. SEO-автопубликация проверяет эту же связь перед
публикацией; независимые статьи SEO-завода продолжают публиковаться
по прежней автоматической политике после критика.

Для связанных публикаций со статусом `scheduled`, `sending` или
`delivery_unknown` нельзя объявить кампанию полностью остановленной:
владелец видит число ожидающих операций и ссылку на раздел публикаций.
При отключённом автопостинге Telegram назначенную публикацию требуется
отменить вручную; автоматический запрос на отмену через внешний API
не выполняется. Отдельные, не привязанные к кампании контент-планы,
публикации и рекламные кабинеты **не управляются** этой командой.
Не называть её «остановкой всех рекламных размещений» или гарантией
отзыва уже отправленных сообщений.

Все переходы проходят Studio Auth/CSRF и изоляцию организаций.
Новых таблиц/миграций не требуется: `Experiment.status` — строковый,
а жизненные события хранятся в существующей таблице `Artifact`.
Обязательные проверки: повторная команда, доступ другого бизнеса,
параллельная отправка, ожидание worker, неопределённая доставка,
независимые материалы и отсутствие побочных публикаций.

Следующий практический этап перед production — интеграционная
проверка на серверном PostgreSQL с параллельными отправителями,
подтверждение жизненного цикла worker и интерфейсное тестирование
в актуальной среде. Только после этого можно рассматривать merge/deploy.
