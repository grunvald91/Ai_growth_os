**Режим работ:** только изменения в черновых GitHub-ветках, CI и локальные/изолированные
данные. **Не выполнять** deployment, migrations в production, изменение nginx,
включение Growth/Mail gateway, перенаправление существующих доменов,
отправку писем, публикацию или запуск платных моделей.

## Кодовые задачи — следующий порядок

1. **Кампании: ручной жизненный цикл выполнен в PR #186.**
   Для статусов `manual_review`, `manual_approved`, `manual_running`,
   `manual_paused`, `manual_completed` есть контролируемые серверные
   переходы, история действий и возможность вернуть черновик на доработку.
   В отличие от `ExperimentLaunchService`, ручная работа не создаёт задания
   и не отправляет рекламу. Перед настоящим запуском рекламного исполнителя
   потребуется отдельная интеграция и пользовательское подтверждение —
   это отложенный практический этап.
2. **SEO-завод: очередь и история статей — выполнено в PR #186.**
   Подтверждение нового задания, безопасная отмена только до захвата worker,
   повтор ошибочного/отменённого задания, ссылки на созданные задания и материалы
   и публикации в блоге при подтверждённом статусе.
   Уже созданные задания на статьи не удаляются при отмене запуска SEO-завода.
   Автоматическая публикация прошедших критика статей существовала ранее и
   не менялась. **Панель критика реализована**: статус для актуальной версии статьи,
   замечания, причины ожидания согласования, переход к полному тексту и ручное
   утверждение через существующий защищённый обработчик Studio.
   Для `servgo` предусмотрен `servgo.ru/blog`. Для остальных компаний принят единый
   вариант — собственная страница и блог на `servgo.ru` без внешних CMS.
   В Growth появился публичный API статей по связанному ID бизнеса BookingBot
   `/public/blog/businesses/{business_id}/articles` и детальный endpoint со ссылками
   `/business/{business_id}` и `/book/{business_id}`. Это **контракт API**, а не готовые
   индексируемые HTML-страницы; запись о публикации не доказывает доступности URL.
   Остались подтверждённые provider costs и обновление статусов без перезагрузки.
   Нулевые CostRecord.amount без cost_known=true не означают бесплатный вызов.
   Running-задание нельзя останавливать простым изменением статуса: оно
   может продолжать платный запрос. Безопасная отмена текущего вызова —
   отдельная задача управления worker.
3. **Настройка агентов и ИИ-команды.**
   Текущая страница настройки промптов остаётся длинной: редактор по одному
   агенту, поиск, свернутые группы, предпросмотр изменений до сохранения,
   без изменения действующего API.
4. **Профиль и аккаунты.**
   Разбить длинные формы на логические разделы без потери полей,
   ссылок, CSRF, прав доступа или старых сохранённых данных.
5. **Mail в едином интерфейсе.**
   Завершить навигационный путь и адаптивный UI контактов, поиска адресатов,
   писем и рассылок на fixture-данных. Не копировать существующий почтовый
   backend и не менять разграничение ролей.
6. **Офлайн для владельца и мастера.**
   Аналогичный Chromium-сценарий холодного запуска `/admin/schedule` и
   `/master`; проверить смену периода/компании, сохранение комментариев и
   телефонов, отсутствие записи без сети. Не превращать это в дополнительный
   запрет на локальное хранение согласованных данных.
7. **Функциональный паритет.**
   Пройти [матрицу 61 функций](SERVGO_FUNCTION_MATRIX.md) на изолированном
   backend с mock-вызовами. Цель — сохранить существующие обработчики и
   права; не запускать реальные рассылки, публикации и платные модели.
8. **Единая тема/переходы.**
   Проверить авторизованные переходы между React, Mail и Growth в
   тестовой среде и отдельно продумать синхронизацию настройки темы
   между устройствами. Локальная тема работает без нового backend-профиля;
   не утверждать обратного.

### Отложено отдельно — практический этап

- Backend/Growth/frontend release, nginx include, TLS, gateway flags;
- реальное SSO с текущими сессиями, ролями и данными production;
- физические Android/iOS PWA, install, offline cold start, push и link capture;
- живые Mail, провайдеры, рассылки и платные модели;
- одновременная работа старых `growth.servgo.ru` и `mail.servgo.ru`
  с новым `servgo.ru` после подключения. Старые адреса не отключать и
  не перенаправлять без решения владельца.

**Критерий для текущей стадии:** работающий код, точечные локальные
проверки и CI на отдельной ветке. Успешный CI не равен production-приёмке;
не требуется повторять проверки бесконечно, если сценарий не менялся.


## Решение: персональный блог каждой компании на ServGo (31.10.2026)

**Внешние сайты клиентов, WordPress, DNS-привязка и серверные учётные данные
исключены из текущего объёма.** Единственная площадка — `servgo.ru`.

- Уже существующая публичная страница BookingBot `/business/{id}` автоматически
  получает имя, описание, адрес, телефон, фотографии, услуги и специалистов
  из таблицы `Business` через `GET /businesses/{id}`. Вторую карточку не создавать.
- Планируемые страницы: `/business/{id}/blog` — лента статей бизнеса,
  `/business/{id}/blog/{slug}` — отдельная индексируемая статья. Главная страница
  бизнеса показывает подборку свежих статей с переходом на блог.
- Рост/SEO уже хранит статьи отдельно по `Product`, а существующий
  `StudioBusinessLink` однозначно связывает `Product` и реальный `business_id`.
  Не связывать компании по названиям, не использовать общий блог разных арендаторов.
- Новый read-only API в Growth `/public/blog/businesses/{id}/articles[/{slug}]`
  возвращает только опубликованные статьи связанных компаний, а детальная статья
  содержит проверенные адреса страницы бизнеса и записи. Для отсутствующего
  business-link — 404, чужие статьи не возвращать.
- На каждой статье показывать настоящие контакты компании и 2 действия:
  «О компании» → `/business/{id}`, «Записаться» → `/book/{id}`.
  Прямой переход к услуге `/book/{id}?service={service_id}` включать лишь после
  строгой проверки `service_id` в актуальном публичном каталоге этого бизнеса;
  нельзя угадывать ID или создавать несуществующую услугу.
- Публикация из SEO-завода автоматическая только после чистой проверки критика
  и статических проверок по уже принятой политике; спорные статьи остаются на
  согласовании. Отдельного ручного копирования в блог компании не требуется.
- Публичные страницы статей должны отдавать индексируемый **HTML на сервере**
  с уникальным title/description, canonical, sitemap и корректными 404.
  Один лишь React SPA/JSON API не считать законченным SEO-размещением.
- Нужна минимальная аналитика `article_id + business_id + source` при переходе
  из статьи на запись; последующие подтверждённые записи связывать с источником
  без доступа публичного читателя к личным данным клиентов.
- При выключении бизнеса или SEO-публикации страница статьи должна перестать
  индексироваться / возвращать 404 по правилам публичной видимости.
  Управление активностью бизнеса является источником истины BookingBot.

**Остаётся в коде:** индексируемый HTML-рендер в BookingBot, список статей на
`BusinessPage`, проверенная маршрутизация по услугам и событие атрибуции.
Изменения nginx/production, live публикации и миграции отложены до
практического этапа.


## SEO-завод — только по явному включению владельца (31.10.2026)

Решение: ни одна компания (включая демо, старые записи, тестовые продукты и
компании, импортированные из BookingBot) не получает SEO-генерацию
автоматически. Отсутствующая строка в `seo_factory_activations` значит
`enabled=false`. Миграция `alembic/versions/0011_seo_factory_opt_in.py`
создаёт только таблицу, **не активирует** ни одного бизнеса.

В авторизованном Growth Studio → «SEO-завод»:
- «Подключить SEO-завод» — явный POST с существующей CSRF/SSO-проверкой.
  У SSO-администраторов нет права включать SEO вместо владельца.
  Подключение само по себе **не** ставит платные задания в очередь.
- После подключения отдельно доступен «Новый запуск SEO-завода» с
  предупреждением о платных запросах. Демо-компании остаются выключенными.
- «Отключить SEO-завод» отменяет только SEO-задачи в очереди данной компании.
  Уже начатый внешний вызов нельзя прервать мгновенно, но новые SEO-задачи
  не стартуют и новые статьи не публикуются. Существующий опубликованный блог
  остаётся виден (не удалять контент пользователей).
- Повторное подключение не восстанавливает старые отменённые задачи.
  Владелец может явно поставить новый запуск.

Защита выполняется на backend: `queue_factory`, `run_factory_once`,
`queue_plan`, `queue_plan_item`, `run_content_once`, `publish_if_clear`,
`publish_owner_approved`, `publish_pending`, а также через
ИИ-диспетчер и ручное повторение SEO-запуска.

Профиль компании Growth Studio уже берётся из BookingBot при первом явном
создании компании через SSO. Создание маркетинговой компании и включение
SEO — **разные действия**. Наличие `StudioBusinessLink` никогда не
должно считаться согласием на SEO-завод.

**Релизный порядок:** сначала применить миграцию 0011 к Growth DB, затем
развернуть новые backend/worker и UI. Перед этим прогнать
`tests/test_seo_activation.py` и CI. Без миграции код с новым opt-in
не должен выкладываться. Production этим изменением не затронут.
