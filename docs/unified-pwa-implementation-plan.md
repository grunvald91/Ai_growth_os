## Непереговорные требования

### Обязательная обратная совместимость действующего Growth URL

- **`https://growth.servgo.ru` остаётся полноценной самостоятельной точкой входа**, независимо от подключения `https://servgo.ru/studio` в едином PWA. Никакого автоматического 301/302 редиректа со старого адреса на новый без отдельного решения владельца.
- Старые ссылки на `/studio`, вложенные страницы, продукты/проекты/задачи и существующие bookmarks должны работать через legacy origin; не менять рабочие URL в ранее отправленных сообщениях.
- Старые входы, существующие сессии/cookies, CSRF/Origin и ограничения прав должны работать как до изменений. Новый origin создаёт **дополнительный** способ доступа к тем же данным и backend, а не новую независимую копию Growth.
- **Не назначать срок отключения legacy домена.** Его сохранение — жёсткий release gate до отдельного явного решения владельца, даже после завершения перехода на единый PWA.


- Одна палитра и компоненты **ServGo Air** для клиентского пути, админки, Growth и Mail. Growth сохраняет полупустую главную, где голосовая строка — главное действие.
- **Один manifest и один service worker** на `servgo.ru` со scope `/`. Backend-процессы можно оставить независимыми; их UI должны быть доступны через один origin.
- Одна настройка `light | dark | system` с серверным предпочтением для пользователя и локальной настройкой до авторизации. Никаких миганий белой темы при переходах.
- Общая оболочка **не** открывает новые права: посетитель, мастер, бизнес-владелец, оператор Growth и платформенный владелец Mail сохраняют свои серверные роли.
- Сохранить операции из [матрицы 61 функции](https://github.com/grunvald91/Ai_growth_os/blob/main/docs/design/SERVGO_FUNCTION_MATRIX.md) и 19 команд диспетчера. UI «Рисованное видео» переименовать в «Простое видео», внутреннее API `whiteboard` оставить.
- Не включать массовые рассылки/публикации в тестах. Все действия с платежами, письмами и публикациями — с подтверждением и проверкой роли.

## Продуктовое решение владельца: офлайн-доступ к рабочему расписанию (31.10.2026)

**Утверждено владельцем ServGo в диалоге:** полное рабочее расписание, имена и телефоны клиентов, услуги, даты/время и комментарии **разрешено хранить локально** на устройстве пользователя с соответствующим доступом. Принцип аналогичен использованию рабочих переписок в мессенджерах: наличие личных/рабочих данных само по себе **не причина отключать полезную функцию**.

**Обязательный продуктовый результат:**
- Установленная PWA открывается после полного закрытия без интернета и показывает последний загруженный набор записей в том же привычном интерфейсе; дата/время последнего обновления заметны пользователю.
- Администратор/владелец просматривает своё расписание, имена, телефоны, услуги, комментарии; мастер — собственное расписание в пределах существующих прав; клиент — свои записи. Локальные данные сохраняют существующие роли и разделение бизнесов.
- Данные при наличии сети обновляются; сетевой сбой не превращает уже сохранённый рабочий экран в пустую страницу. Для новых устройств или ранее не загруженных периодов указывается, что данные ещё не сохранены.
- Технически разделить **offline app shell** (общая статическая оболочка: безопасный HTML, JS/CSS, шрифты) и **offline domain data** (локальная IndexedDB с явно структурированными данными расписания/записей). SW v3 предотвращает ошибку общего кеша HTML и не является запретом на локальные данные.
- Разработать отдельные регрессионные тесты: cold start PWA без сети, ранее загруженные записи, обновление сети, переключение периода, несколько бизнесов/ролей, сохранение комментариев и телефонов, не-утечка между аккаунтами. Не заявлять об офлайн-режиме до реального device E2E.

**Дополнительное решение владельца:** локальное хранение расписания/записей **7 дней** с момента получения данных; **очистка при выходе**; **без интернета только просмотр**, создание/изменение/перенос/отмена/подтверждение — лишь онлайн, без очереди синхронизации. Не согласовано и НЕ должно молча превращаться в запрет: PIN/шифрование и UX, хранение Mail/Growth, иные ограничения. Обсуждать конкретный риск, альтернативы и ущерб для функций до внедрения. Существующие разграничения прав бизнесов остаются.

**Актуальная граница:** уже выпущенный SW v3 (31.10.2026) пока network-only на HTML и в офлайне отдаёт нейтральный экран; это временное техническое состояние, **не целевое продуктово утверждённое ограничение**. Новую offline-функцию вести отдельным PR/этапом с проверкой старой PWA и без переключения Growth/Mail gateway до её готовности.

## Целевые внешние URL (ещё НЕ существуют как готовые UI)

| Раздел | Внешний путь | Источник |
|---|---|---|
| Клиентский путь | `/`, `/business/:id`, `/book/:id`, `/my` | BookingBot React |
| Админка | `/admin/*` | BookingBot React |
| Growth | `/workspace/growth/*` | Growth OS через same-origin gateway |
| Mail | `/workspace/mail/*` | ServGo Mail через same-origin gateway |
| Growth API | `/api/growth/*` | API gateway / проверка ролей |
| Mail API | `/api/mail/*` | API gateway / mail_owner |

**Нельзя просто проксировать HTML на подмаршрут:** Growth содержит абсолютные `/studio/*`/`/products/*`, а Mail использует `/api/*`, `/claim`, отдельную cookie и `Origin == https://mail.servgo.ru`. Прежде нужны адаптеры URL, assets, redirect, CSRF и SSO. Внешняя ссылка на другой origin не гарантирует сохранение standalone PWA; экспериментальные scope_extensions не являются основным решением.

## Блокирующие требования безопасности

- **CacheStorage SW v3 (текущее состояние):** только публичная статика; не сохранять в общий HTTP-кеш HTML из чужой авторизованной сессии, вложения или подписанные URL. **Это не запрет на локальные рабочие данные:** согласованный offline app shell и IndexedDB для расписаний/контактов/комментариев будут разработаны отдельным этапом. Нейтральный экран — текущий fallback до внедрения просмотра сохранённых данных.
- **Legacy SW**: удалить cache `servgo-pwa-v2`, не затронуть чужие cache namespace и существующую push подписку.
- **Mail**: сохранить `mail_owner` только платформенному владельцу; не делать cookie с `Domain=.servgo.ru` для упрощения входа. Требуются one-time ticket с TTL/audience, HttpOnly Secure host-only cookie и анти-CSRF.
- **Growth**: сохранить tenant-scope, запрет доступа к чужой компании, текущую защиту POST/PUT и строгий CSP ИИ-команды.
- **Logout**: без возможности прочитать последнюю чужую страницу из service worker/history после выхода.
- **PWA**: нативные ссылки только через same-origin. Поддержку открытия установленного PWA из внешних мессенджеров отдельно проверять на разных ОС — она не гарантирована для всех браузеров.
