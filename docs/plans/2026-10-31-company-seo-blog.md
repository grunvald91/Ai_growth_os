# ServGo — единый блог каждой компании (31.10.2026)

## Продуктовое решение

SEO-завод публикует статьи **только на ServGo**. Интеграции с внешними сайтами,
WordPress, доступы к серверам клиентов и отдельные домены в объём не входят.

У компании уже есть страница `/business/{id}`, которая подгружает реальные
публичные данные (имя, описание, фотографии, адрес, телефон, услуги, мастеров)
из BookingBot. Её не дублируем. Добавляем к ней блок последних опубликованных
статей и два клиентских маршрута:

- `/business/{id}/blog` — блог конкретной компании;
- `/business/{id}/blog/{slug}` — статья, ссылки «О компании» и «Записаться».

Кнопка записи ведёт на действующий маршрут `/book/{id}`. Уже существующий
`BookingPage` поддерживает `?service={service_id}`, но авто-выбор конкретной
услуги из статьи пока **не включён**: сначала нужен проверенный ID в каталоге
услуг этой компании, а не совпадение текста.

## Источник статей и разделение компаний

Growth OS — источник статей, проверки критиком и статуса публикации.
База BookingBot — источник карточки компании и активных услуг.
В Growth существует таблица `StudioBusinessLink`, которая связывает
`business_id` из BookingBot и `product_id` из маркетинговой студии.

Growth API (read-only):
- `GET /public/blog/businesses/{id}/articles`
- `GET /public/blog/businesses/{id}/articles/{slug}`

Growth возвращает только опубликованные артефакты `own_site`, только для
привязанного бизнеса; не связанный ID возвращает 404.

BookingBot не хранит вторую копию статей и не предоставляет доступ к Growth
студии из браузера клиента. Он получает контент через свой серверный
read-only proxy:
- `GET /api/businesses/{id}/blog/articles`
- `GET /api/businesses/{id}/blog/articles/{slug}`

Внутренний HTTP-клиент BookingBot обращается к
`GROWTH_PUBLIC_BLOG_URL` (по умолчанию `https://growth.servgo.ru`).
Если upstream недоступен, профиль и запись продолжают работать;
блог скрывается на карточке, а отдельная страница показывает
понятное сообщение. Для неактивного бизнеса возвращается 404.
Адрес upstream нельзя задать посетителю, параметры статьи ограничены slug.

## Уже подготовлено в review-коде

- Изолированный публичный Growth API по реальному идентификатору компании;
- backend-прокси BookingBot без CORS-настроек для браузера;
- React-страницы блога/статьи и блок ссылок на бизнес-карточке;
- CTA к существующему пути записи без догадок о номере услуги;
- точечные проверки связи компаний, скрытых публикаций и API-прокси.

## Что обязательно закончить до фактического SEO-запуска

1. **Индексируемые страницы.** Нынешние React-маршруты загружают статью
   клиентским запросом; это полезный UI, но не доказательство полноценной
   индексации. Добавить серверный HTML-рендер или пререндер с уникальными
   title/description, canonical, корректными 404, sitemap и robots.
   Конфигурацию nginx проверить в отложенном практическом этапе.
2. **Активность бизнеса.** Growth хранит публикацию, а BookingBot знает
   `Business.is_active`. Публичный рендер не должен отдавать статью
   неактивной компании.
3. **Переход в услугу.** При необходимости добавить `service_id` к проверенным
   публичным данным услуги и резолвер внутри BookingBot; с гарантированным
   fallback на `/book/{id}`.
4. **Аналитика.** Пронести через статью и запись безопасный источник
   `business_id/article_id` и измерять подтверждённые бронирования;
   не передавать персональные данные в открытые SEO-URL.
5. **Завершение.** CI двух интеграционных веток + изолированные тесты;
   никаких production-правок, реальных публикаций и платных вызовов на
   текущем кодовом этапе.
