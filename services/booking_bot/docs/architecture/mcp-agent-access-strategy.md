# ServGo — MCP / Agent Access: архитектурная стратегия

**Статус:** APPROVED STRATEGY / NOT IMPLEMENTED  
**Дата решения:** 2026-10-12  
**Область:** ServGo — единая платформа записи для нескольких бизнесов; AI Growth OS может использовать те же прикладные сервисы через явно разрешённые интеграции.

## Цель

Сделать услуги компаний на ServGo доступными внешним ИИ-агентам: находить компанию, изучать услуги и цены, проверять свободное время и — только с необходимой авторизацией и подтверждением — создавать, переносить или отменять запись.

MCP (Model Context Protocol) — **один из интерфейсов**, а не замена сайту, Telegram, SEO, публичным страницам, обычному API или бизнес-логике.

Наличие MCP **не означает автоматическое обнаружение** ServGo всеми ИИ-ассистентами. Подключение, публикация и доступность зависят от конкретной платформы и её правил.

## Принцип архитектуры

~~~text
Клиенты: сайт / Telegram / внутренний API / внешние ИИ-агенты
                                            |
                                   MCP gateway (HTTPS)
                                            |
                            identity, consent, scopes, tenant
                                            |
            единые application services / бизнес-правила ServGo
                                            |
     каталог / расписание / бронь / предоплата / уведомления
                                            |
                         текущее хранилище ServGo
~~~

- Отдельный тонкий MCP-адаптер вызывает **существующие сервисы предметной области**, а не пишет в БД напрямую.
- Не создавать отдельный движок бронирования или копию календаря для ИИ.
- Для каждого запроса определять бизнес/tenant и права **на сервере**. Переданный агентом business_id никогда сам по себе не является разрешением.
- Модель, промпт и описания MCP-инструментов не являются доверенной границей безопасности.
- Разделять публичную информацию компании и персональные данные клиентов, сотрудников и владельцев.
- Все интерфейсы должны сохранять одинаковые правила: доступность слота, рабочие часы, блокировки, переносы, отмены, уведомления и подтверждение платежа.

## Планируемые MCP tools (имена предварительные)

| Инструмент | Назначение | Доступ |
| --- | --- | --- |
| find_businesses | Найти публичные компании по местоположению, категории, фильтрам | Только публичные / разрешённые к индексации данные |
| list_services | Услуги, описания, цены и условия | Публичное чтение |
| get_availability | Проверка свободных слотов по услуге, дате, мастеру и часовому поясу | Публичное чтение без чужих записей |
| get_booking | Получение **своей** записи / разрешённого ресурса | Аутентификация, booking:read |
| create_booking | Создание записи через существующий use case | Аутентификация, booking:write, подтверждение |
| reschedule_booking | Перенос своей записи по правилам бизнеса | Аутентификация, booking:write, подтверждение |
| cancel_booking | Отмена своей записи по правилам бизнеса | Аутентификация, booking:write, подтверждение |

Масштабы полномочий (scopes) здесь **проектные**, а не уже существующие OAuth-права. Инструменты и схемы уточняются при реализации и не должны показывать чужую персональную информацию.

## Обязательные инварианты безопасности и записи

1. Веб-доступ: HTTPS, актуальный MCP Streamable HTTP, проверка Origin, аутентификация/авторизация в соответствии с выбранной версией спецификации и поддерживаемыми клиентами.
2. Для защищённых операций — проверка токенов, audience/resource, scopes, принадлежности booking к клиенту, бизнесу и роли; запрет передачи пользовательских токенов другим сервисам (token passthrough).
3. Для действий, изменяющих запись, — проверяемое согласие/подтверждение пользователя. Одного текста «пользователь согласен», присланного агентом, недостаточно; подтверждение и авторизация должны проверяться backend.
4. Повторная проверка доступности и атомарная фиксация брони в существующей логике ServGo; защита от гонок и двойной записи. Idempotency key для повторов со стороны агентов.
5. Учитывать, что запись может требовать предоплату: MCP **не подтверждает поступление денег** и не обходит существующее подтверждение владельцем. Возвращать фактический статус pending/confirmed, а не обещать подтверждение заранее.
6. Структурированные схемы входа/выхода, валидация, rate limit, таймауты, аудит операций без раскрытия секретов и избыточных ПДн.
7. Для бизнеса — управление видимостью каталога и возможность отключить агентский канал. Хранение и передача персональных данных должны соответствовать применимому законодательству РФ; до запуска нужна отдельная правовая проверка.
8. Отдельные тесты на межтенантную утечку, подмену ID, чужие записи, повторные вызовы, просроченные токены, недоступные слоты, отмены и ошибки внешнего клиента.

## Этапы реализации

**Этап A — подготовка домена.** Инвентаризировать реальный backend/API и сценарии записи; выделить переиспользуемые application services без обхода бизнес-правил. Подготовить публичные структурированные данные и страницы компаний (SEO независимо от MCP). Никакого деплоя MCP на этом этапе.

**Этап B — read-only MVP.** MCP gateway с find_businesses, list_services, get_availability; тесты на публичность, изоляцию tenant, rate limit, актуальность слотов и совместимость с конкретными MCP-клиентами.

**Этап C — безопасные операции.** OAuth/разрешения, подтверждение пользователя, create_booking/get_booking; затем перенос и отмена. Атомарность, идемпотентность, статусы оплаты и аудит обязательны до публичного включения.

**Этап D — дистрибуция.** При наличии подтверждённой совместимости — подключение выбранных агентских платформ, регистрация/публикация по их правилам, тестовый сценарий «найди услугу → покажи слоты → подтверди → запиши». Не заявлять интеграции до фактического тестирования.

**Этап E — измерение.** Отдельно учитывать число найденных бизнесов, запросов слотов, подтверждённых агентских бронирований, ошибок/конфликтов, отмен и обращений в поддержку. Эти метрики — будущие показатели, не текущие результаты.

## Критерии приёмки

- Внешний MCP-клиент на тестовом контуре получает только допустимые публичные данные.
- Аутентифицированный агент не может читать/менять записи чужих клиентов и tenant.
- Одновременные запросы не создают двойной брони; повторы не создают дублей.
- Платёж и уведомления проходят **тот же** жизненный цикл, что и запись через сайт/Telegram.
- Нет возможности выполнить критическое действие без проверяемого подтверждения.
- Есть интеграционные и негативные тесты, документация по авторизации, логирование ошибок и процедура отключения MCP без нарушения обычной записи.
- Развёртывание — отдельное решение после проверок; минимизировать GitHub Actions, предпочтительны локальные тесты и согласованный SSH-деплой.

## Границы решения

Это **архитектурное намерение**, не описание действующих endpoints или готового MCP-сервера. Конкретные классы, таблицы, хосты и версии библиотек выбираются после проверки актуального кода.

AI Growth OS не получает по умолчанию доступ к персональным данным клиентов и не обходит публичные контуры авторизации/подтверждений.
