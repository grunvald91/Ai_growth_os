# Редизайн клиентского флоу под ds-* дизайн-систему + цвета логотипа

## Контекст

Админ-панель (`web/frontend/src/pages/admin/*`) уже переведена на единую
дизайн-систему `web/frontend/src/styles/design-system.css` (токены `--s-*`,
классы `ds-*`) и полноэкранный «mini-app» каркас `AdminShell.tsx`
(`createPortal` в `document.body`, нижняя навигация на мобильном → боковая
колонка на десктопе ≥900px).

Клиентский флоу (`web/frontend/src/pages/client/*`) остаётся на старой
Tailwind-теме `apple-*` и общем `components/Layout.tsx` (шапка сверху +
скролл страницы + нижняя навигация только на мобильном). Задача — привести
клиентский флоу к тому же визуальному языку и уровню отделки, что и админка,
и завязать акцентный цвет всего приложения на цвета логотипа (`Logo.tsx`).

## Цели

1. Все 7 клиентских экранов (Главная, Страница бизнеса, Запись, Мои записи,
   Абонементы, Вход, AI-чат) выглядят и ведут себя как «mini-app» — так же,
   как уже сделанная админка.
2. Единый акцентный цвет по всему приложению (админка + клиент), взятый из
   логотипа, а не из присланного ранее макета админки.
3. Ни один API-вызов, ни одна ветка бизнес-логики не меняются — только
   презентационный слой (разметка/классы/стили).

## Решения (согласованы с пользователем)

- **Масштаб**: весь клиентский флоу, все 7 экранов + общий каркас.
- **Акцент**: единый по всему приложению, включая уже сделанную админку —
  `#2ea6ff` → `#2F5BEB` (логотип) в светлой теме; в тёмной — `#7FA0FF`
  (светлый вариант синего из логотипа, лучше читается на тёмном фоне).
- **Каркас клиента**: новый `ClientShell.tsx` по образцу `AdminShell.tsx` —
  тот же паттерн `createPortal`, полноэкранный `ds-screen`, нижняя
  навигация/боковая на десктопе. `Layout.tsx` остаётся в коде, но перестаёт
  визуально рендериться (как и для админки после её portal-фикса) — известный
  и принятый техдолг, не убираем сейчас.
- **Навигация**: показывается на всех экранах, включая детальные (страница
  бизнеса, запись, вход) — так же, как сейчас в `Layout.tsx`.
- **Тема**: клиент получает переключатель светлая/тёмная (переиспользуем
  `useTheme`), для визуальной консистентности с админкой.

## Архитектура

### `ClientShell.tsx` (новый компонент)

Аналог `AdminShell.tsx`:

- `createPortal(..., document.body)` — полноэкранный `ds-screen`,
  `data-theme={theme}`.
- Шапка: логотип/заголовок; на детальных экранах (Страница бизнеса, Запись) —
  back-стрелка вместо логотипа + короткий заголовок (например, имя бизнеса).
  Пропсы: `title`, `backTo?`, `headerExtra?` (по аналогии с `AdminShell`).
- Контент: `ds-shell-content`, скроллируемый.
- Нижняя навигация `ds-bottomnav`/`ds-bn`, 5 пунктов: Главная (`/`),
  Мои записи (`/my`), Абонементы (`/subscriptions`), AI (`/chat`),
  Профиль/Войти (аутентификация — открывает панель профиля или ведёт на
  `/login`, логика 1-в-1 переносится из текущего `Layout.tsx`).
- Десктопная раскладка (боковая колонка) уже описана в
  `design-system.css` через классы `ds-screen`/`ds-shell-header`/
  `ds-shell-content`/`ds-bottomnav`/`ds-bn` — новых media-query не требуется,
  `ClientShell` их просто переиспользует.

### Цветовые токены (`design-system.css`)

```
светлая тема:
  --s-accent:        #2ea6ff → #2F5BEB
  --s-accent-press:  #2a7cf0 → #244BD6
  --s-accent-ink:    #04121f → #FFFFFF   (тёмный текст нечитаем на насыщенном синем)
  --s-accent-soft:   пересчитать rgba от нового --s-accent

тёмная тема:
  --s-accent:        #2ea6ff → #7FA0FF
  --s-accent-ink:    остаётся тёмным (#0D1B2A, цвет текста логотипа)
  --s-accent-soft:   пересчитать rgba от нового --s-accent
```

Изменение затрагивает все компоненты, использующие `var(--s-accent*)` —
включая уже сделанную админку (кнопки, чипы, сегменты, FAB, полоса «сейчас» в
расписании и т.д.). Ожидаемый эффект — точечная перекраска, без изменений
разметки.

### Маппинг страниц на ds-* (без изменения логики/API)

| Страница | Ключевые ds-* замены |
|---|---|
| **HomePage** | `ds-h1`/`ds-sub` для hero, сетка бизнесов на `ds-card` |
| **BusinessPage** | шапка с back-стрелкой, инфо-пилюли, сетка мастеров на `ds-card`, модалка мастера → `ds-sheet` вместо кастомного fixed-модала, кнопка «Записаться» → `ds-btn--primary ds-btn--block` |
| **LoginPage** | `ds-field`/`ds-input`, кнопка `ds-btn--primary ds-btn--block`, цифры кода — вариант `ds-input` под квадратные поля |
| **ChatPage** | пузыри сообщений на токенах (акцент — сообщения пользователя), поле ввода в стиле `ds-search` |
| **MyBookingsPage** | карточки записей → `ds-row` (уже спроектирован под «время + услуга/клиент»), статусы → готовые `ds-badge--pending/confirmed/completed/cancelled/prepay`, отмена → `ds-dialog` |
| **SubscriptionsPage** | табы → `ds-seg--full`, карточки → `ds-card`, покупка (3 шага) → `ds-sheet` |
| **BookingPage** (2075 строк, отдельный проход) | `ds-card`/`ds-btn`/`ds-field` точечно; календарь/сетка слотов — специфичны, выносятся в отдельный `booking.css` (по образцу `schedule.css`) со своими `.bk-*` классами; логика/ветвление (venue vs услуга, предоплата, addon-часы) не трогается |

## Порядок выполнения

1. Создать `ClientShell.tsx`, применить перекраску токенов в
   `design-system.css`, собрать и визуально проверить, что админка не
   сломалась (light/dark, mobile/desktop).
2. Параллельные агенты — по одному независимому файлу: HomePage,
   BusinessPage, LoginPage, ChatPage, MyBookingsPage, SubscriptionsPage.
   Каждому — чёткая граница: сохранить всю логику/API-вызовы, заменить
   только презентационную разметку на `ds-*`, обернуть в `ClientShell`,
   не запускать build (во избежание конфликтов при параллельной работе).
3. Отдельно и аккуратно (не агентом-конвейером, а вручную/с повышенным
   вниманием) — `BookingPage.tsx`, как денежный флоу с самой высокой ценой
   регрессии.
4. Проверка в браузере (мобильный 390×844 и десктоп 1280×800, светлая и
   тёмная тема, авторизован/не авторизован) по всем 7 экранам — тем же
   харнессом, что использовался для админки (`mock.js` + `spaserve.py` +
   Playwright), включая эмуляцию `html.tg-webapp` для проверки отступа под
   нативную шапку Telegram (см. регресс, найденный и исправленный в админке
   ранее в этой сессии).
5. `npm run build` (или `vite build`, т.к. `tsc -b` уже красный на
   предсуществующем баге в `BookingPage.tsx`, не связанном с этой задачей),
   коммит, деплой на прод по SFTP (paramiko).

## Риски и границы

- **BookingPage** — самый большой риск регрессии (денежный флоу,
  ветвление venue/услуга, async загрузка слотов/цены, localStorage-кэш
  токена публичной брони). Изолируем отдельным проходом с ручной проверкой
  каждого шага мастера, а не доверяем агенту-конвейеру наравне с простыми
  страницами.
- **Layout.tsx остаётся мёртвым кодом** визуально (как и для админки) —
  не убираем в рамках этой задачи.
- **`tsc -b` уже красный** на несвязанном предсуществующем баге
  (`prepaymentSentByToken`/`uploadReceiptByToken` в `BookingPage.tsx` —
  задокументировано в project-памяти), поэтому сборка для проверки/деплоя
  идёт через `vite build` напрямую, как и для админки.
