# Повторяющаяся еженедельная запись (2–8 недель)

## Контекст

Сейчас запись (и клиентская через `POST /bookings`, и ручная админская через
`POST /admin/bookings`) всегда создаёт бронь на одну конкретную дату/время.
Постоянным клиентам (стрижка каждую среду в 18:00 и т.п.) приходится
записываться заново каждую неделю. Нужна возможность сразу забронировать
тот же день недели/время/услугу/мастера на несколько недель вперёд —
и в клиентском флоу записи, и в ручной записи владельца через расписание.

## Цели

1. Клиент и владелец могут при создании записи включить "Повторять каждую
   неделю" и выбрать количество недель — от 2 до 8 (включая первую).
2. Если хотя бы одна из недель конфликтует по времени — не создаётся ни
   одной записи серии, пользователь получает понятную ошибку с датой
   конфликта.
3. Никакой новой сущности "серия" не вводим — N записей полностью
   независимы друг от друга (отмена/перенос/статус — как у обычной брони).

## Явно вне рамок первой версии

- Повтор для записи, оплачиваемой абонементом (списание N сессий разом) —
  кнопка повтора скрыта, если выбрана оплата абонементом.
- Групповая отмена/перенос "этой и всех следующих".
- Изменение шага повтора (только еженедельно, не раз в 2 недели и т.п.).

## Backend

### `POST /bookings` (`web/api/routes/client.py`)

- `CreateBookingIn` получает новое поле `repeat_weeks: Optional[int] = None`
  (валидация 2–8, `None`/отсутствие = как сейчас, одна дата).
- Если `repeat_weeks` задан: вычисляются даты `date`, `date+7`, `date+14`, ...,
  всего `repeat_weeks` дат (все с тем же временем/сервисами/мастером/солю-
  режимом, что и переданные в теле запроса — как за один и тот же визит).
- **Двухфазная обработка**: сначала по каждой дате прогоняется та же
  проверка конфликта, что уже есть для одиночной записи (включая цикл по
  `service_ids` для мульти-услуг за визит), но **без записи в БД** — просто
  собираем список конфликтов. Если список конфликтов не пуст — `409` с
  телом вида `{"detail": "Занято: 12.08 15:00, 26.08 15:00"}` (человеко-
  читаемые даты), ничего не создано.
- Если конфликтов нет — второй проход реально создаёт все Booking-записи
  (тот же код пути, что и сейчас для одной даты, просто в цикле по датам)
  в рамках одной транзакции/коммита.
- Ответ остаётся `List[BookingOut]` (сейчас уже список из-за мульти-услуг за
  визит) — при повторе туда просто попадают все N×услуг записей.

### `POST /admin/bookings` (`web/api/routes/admin.py`)

- `ManualBookingIn` получает то же поле `repeat_weeks: Optional[int] = None`.
- **Важное изменение поведения**: сейчас ручная запись НЕ проверяет
  конфликты вообще (админ считается доверенным при работе через календарь
  день-в-день). Для повторяющейся записи конфликты проверяются — за 8 недель
  вперёд визуально свериться с расписанием нереально. Проверка — та же
  двухфазная схема, что и в клиентском эндпоинте (свой набор конфликт-
  фильтров, т.к. `ManualBookingIn` не поддерживает мульти-услуги за визит,
  проверяем по одной услуге/мастеру на дату).
- Response model меняется с `AdminBookingOut` на `List[AdminBookingOut]`
  (всегда список — при отсутствии `repeat_weeks` список из одного элемента).
  Это единственное изменение контракта существующего эндпоинта — фронт
  (`api.createManualBooking` и вызывающий код в `ManualBookingModal`)
  обновляется соответственно.

### Общий хелпер

Логика "посчитать N дат от стартовой + weekly" — небольшая чистая функция
(без сайд-эффектов), переиспользуется в обоих роутах, живёт в
`web/api/routes/client.py` или отдельном `web/api/booking_utils.py` (решается
на этапе реализации по факту, куда лучше ляжет без циклического импорта).

## Frontend

### Клиентская запись (`web/frontend/src/pages/client/BookingPage.tsx`)

- На шаге подтверждения (там же, где сейчас имя/телефон/комментарий) —
  новый блок: `ds-seg--full`-переключатель "Разово" / "Повторять" +, если
  включено "Повторять", степпер количества недель 2–8 (аналогичный уже
  существующим steppers по доп.услугам).
- Под степпером — короткая подсказка: "Ещё N−1 такие же записи каждую
  неделю после первой".
- Блок скрыт/недоступен, если текущая оплата — через абонемент.
- `api.createBooking` прокидывает `repeat_weeks` в теле запроса, когда
  переключатель включён.
- Экран успеха: если создано больше одной записи — вместо одной даты/
  времени показываем список всех дат серии (переиспользуем существующую
  вёрстку сводки, просто маппим по массиву дат).
- Ошибка конфликта (`409` с деталями) показывается в существующем месте
  вывода ошибок формы (`ds-error`), без создания частичной серии.

### Админ ручная запись (`ManualBookingModal` в `SchedulePage.tsx`)

- Тот же переключатель + степпер в форме модалки (после выбора даты/
  времени/мастера/услуги).
- `api.createManualBooking` возвращает список — модалка после успеха
  закрывается и обновляет расписание (`fetchBookings()`), плюс короткий
  toast "Создано N записей" при `repeat_weeks > 1` (при обычной записи —
  без изменений, как сейчас).
- Ошибка конфликта — как обычная ошибка формы, ничего не создаётся.

## Обработка ошибок и граничные случаи

- Конфликт хотя бы одной недели → `409`, ничего не создано, сообщение с
  датой(ами) конфликта.
- `repeat_weeks` вне диапазона 2–8 → `422` (валидация Pydantic).
- Услуга/мастер недоступны на какую-то из будущих дат по иной причине
  (например, услуга деактивирована задним числом) — не в рамках этой
  фичи, ведёт себя так же, как повлияло бы на одиночную запись сегодня
  (сообщение "услуга не найдена" и т.п.), просто в контексте двухфазной
  проверки конфликтов.
- Часовой пояс/переход на летнее время — не учитываем отдельно, даты
  считаются календарно (+7 дней), как и весь остальной календарь в проекте.
