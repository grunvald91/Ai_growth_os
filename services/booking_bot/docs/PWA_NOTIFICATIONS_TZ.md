# ServGo — PWA, напоминания и календарь

## Цель

Убрать Telegram как единственную точку доставки клиентских уведомлений и превратить web-frontend ServGo в устанавливаемое PWA-приложение с Web Push. При этом сохранить Telegram как дополнительный канал и дать клиенту независимый резервный способ напоминания через системный календарь.

## Текущее состояние и выявленные проблемы

1. Новый frontend `web/frontend` — обычный React/Vite SPA: manifest и service worker отсутствуют.
2. Клиентские напоминания за 24 часа и за 2 часа существуют, но транспорт жёстко связан с Telegram (`bot.send_message`).
3. Scheduler проверяет напоминания раз в 5 минут и ищет запись только в окне ±5 минут вокруг целевого времени. Если процесс/сервер отсутствует дольше окна, напоминание может быть потеряно.
4. Флаги `reminder_24h_sent` и `reminder_2h_sent` не различают каналы доставки.
5. Вход по телефону всё ещё отправляет код через Telegram. Это отдельная зависимость, которую необходимо убрать перед позиционированием ServGo как полностью независимого от Telegram.
6. В коде смешаны локальное время и UTC. Для текущего Sochi-сценария требуется явная бизнес-таймзона; перед международным запуском таймзона должна стать полем Business.
7. Чистая PWA не гарантирует локальное уведомление ровно в заданное время при полном отсутствии сети. Для такого режима нужен native-слой (рекомендуемый следующий этап — Capacitor Local Notifications).
8. В web phone-auth был hardcoded fallback Telegram bot token. В этой ветке fallback удалён; production должен получать BOT_TOKEN только из secret/env. Поскольку значение уже попадало в историю Git, после внедрения токен следует перевыпустить.
9. Client/admin reschedule ранее не сбрасывали reminder_24h_sent/reminder_2h_sent; в этой ветке флаги сбрасываются при переносе, чтобы новая дата получила новые напоминания. Legacy webapp уже делал такой сброс.

## Этап 1 — PWA (в этой ветке)

### Frontend

- Добавить `manifest.webmanifest`.
- Добавить Service Worker.
- Зарегистрировать Service Worker при старте приложения.
- Кэшировать application shell и статику; не кэшировать `/api/*`.
- Для навигации использовать network-first с offline fallback.
- Для статических файлов использовать cache-first/stale cache.
- Обработать `push` и `notificationclick`.
- Добавить пользовательский install prompt:
  - Chromium/Android — через `beforeinstallprompt`;
  - iOS — понятная подсказка «Поделиться → На экран Домой».
- Добавить PWA meta-теги в `index.html`.

### Definition of Done

- ServGo распознаётся браузером как устанавливаемое web app.
- После установки запускается в standalone-режиме.
- При временной потере сети открывается ранее закэшированная оболочка приложения.
- API-запросы никогда не обслуживаются устаревшим кэшем.

## Этап 2 — Web Push (в этой ветке)

### Конфигурация

Обязательные переменные окружения:

- `VAPID_PUBLIC_KEY`
- `VAPID_PRIVATE_KEY`
- `VAPID_SUBJECT` (например `mailto:...`)

Ключи не коммитятся в Git. Для генерации добавлен `scripts/generate_vapid_keys.py`; private key после генерации хранится только в secret/env.

### База данных

Новая таблица `push_subscriptions`:

- `user_id`
- `endpoint` (unique)
- `p256dh`
- `auth`
- `is_active`
- `failure_count`
- `last_success_at`
- timestamps

Подписка может быть привязана:
- к авторизованному пользователю;
- к владельцу брони по секретному `notify_token` сразу после гостевой web-записи.

### API

- `GET /api/notifications/vapid-public-key`
- `POST /api/notifications/subscribe`
- `DELETE /api/notifications/subscribe`

### Frontend UX

После создания брони показывать:
- «Включить напоминания»;
- состояние «Напоминания ServGo включены»;
- понятное сообщение при запрете уведомлений.

В разделе «Мои записи» также должна быть возможность включить Web Push.

### Delivery

Web Push отправляется параллельно Telegram:
- напоминание о записи;
- напоминание за 2 часа.

Недействительные push endpoints (HTTP 404/410) деактивируются.

## Этап 3 — исправление scheduler (в этой ветке — минимально безопасное)

Убрать зависимость от точного окна ±5 минут.

Правило:
- 24h reminder считается due, если запись ещё в будущем, до неё <= 24 часов, но > 2 часов, и напоминание ещё не доставлено;
- 2h reminder считается due, если запись ещё в будущем и до неё <= 2 часов, и напоминание ещё не доставлено.

Такой алгоритм переживает рестарт процесса и не теряет запись только потому, что сервер не работал в конкретное 10-минутное окно.

### Следующий обязательный hardening

Перейти от двух boolean-полей к таблице `notification_jobs` / `notification_deliveries` с полями:

- booking/visit id
- reminder kind
- channel
- scheduled_at
- status
- attempts
- sent_at
- last_error

Это позволит независимо ретраить Telegram/Web Push/SMS и видеть реальную доставку каждого канала.

## Этап 4 — «Добавить в календарь» (в этой ветке)

Клиент может скачать `.ics` для записи.

Событие содержит:
- бизнес;
- услугу;
- дату и время;
- адрес;
- длительность (если известна);
- VALARM за 24 часа;
- VALARM за 2 часа.

На success-screen кнопка показывается сразу после успешной записи. В «Мои записи» кнопка доступна для будущих записей.

Текущий default timezone: `Europe/Moscow`. Перед подключением бизнесов из других часовых поясов добавить `Business.timezone` (IANA identifier).

## Этап 5 — полная автономность без интернета (следующая ветка)

PWA Web Push требует получения push-сообщения через сеть. Для гарантированного локального уведомления при полном offline:

1. Обернуть существующий React/Vite frontend в Capacitor.
2. Подключить Local Notifications.
3. При создании/синхронизации брони планировать local notification:
   - за 24 часа;
   - за 2 часа.
4. При переносе брони отменять старые local notifications и планировать новые.
5. При отмене брони удалять local notifications.
6. При повторном запуске приложения сверять локальные alarms с серверной правдой.
7. Telegram/Web Push/SMS оставить серверными дополнительными каналами.

## Отдельно: убрать Telegram из авторизации

Текущий phone-login отправляет одноразовый код через Telegram. Это противоречит цели независимости.

Нужен отдельный этап:
- SMS-провайдер либо email/другой независимый OTP;
- Telegram Login оставить как быстрый дополнительный способ;
- коды не хранить in-memory: использовать существующую/отдельную таблицу OTP с TTL, attempt counter и one-time consumption.

## Безопасность

- VAPID private key — только secret/env.
- `notify_token` не логировать и не показывать посторонним.
- Push subscription endpoint считать чувствительным идентификатором и не писать целиком в обычные application logs.
- Subscription endpoints не должны позволять произвольно привязать endpoint к чужому user_id.
- Service Worker не кэширует authenticated API responses.

## Acceptance checklist

- [ ] Android Chrome предлагает установить ServGo.
- [ ] PWA запускается standalone.
- [ ] Web Push подписка сохраняется на backend.
- [ ] Гостевой клиент может подписаться по `notify_token`.
- [ ] Push приходит при закрытом PWA (при наличии сети).
- [ ] Клик по push открывает нужную бронь/`/my`.
- [ ] Telegram продолжает работать как дополнительный канал.
- [ ] Рестарт scheduler не приводит к пропуску due-напоминаний.
- [ ] Календарный `.ics` импортируется и содержит два VALARM.
- [ ] Отмена/перенос не создают ложную уверенность: Web Push берёт актуальное состояние с сервера; local offline alarms будут реализованы только на Capacitor-этапе.


## Выявленный существующий frontend tech debt

На момент этой работы `web/frontend/package.json` содержит Vite 8 и `@tailwindcss/vite 4.2.1`. Эта комбинация вызывает npm peer-dependency conflict при обычном `npm ci`. PWA CI временно использует `npm ci --legacy-peer-deps`, чтобы валидировать изменения этой ветки без незапланированного обновления frontend-зависимостей. Отдельной задачей следует обновить Tailwind Vite integration до версии с официальной поддержкой Vite 8 и вернуть строгий `npm ci`.
