# ServGo: единый вход через VK ID (основной сайт и Studio)

**Статус:** PR #145; не выложено на production. Система авторизации VK в PR #297 сервиса Growth Studio для *подключения группы к публикациям* — отдельная интеграция, она не даёт доступ к личному аккаунту ServGo.

## Что получит пользователь

- На `https://servgo.ru/login`: «Войти через VK ID» (доступна только когда администратор настроил VK приложение).
- После входа: обычная сессия и права ServGo, без новых организаций и без отдельной учётной записи Studio. Переход на `https://servgo.ru/studio` через существующий SSO.
- На `https://servgo.ru/account`: «Привязать VK ID». Вход по VK впоследствии открывает те же организации.
- Если VK ID прежде создавал отдельный *только VK* аккаунт, владелец может подтвердить его объединение с текущим авторизованным аккаунтом; переход прав выполняет уже действующая процедура `move_account_data` с транзакционными блокировками и защитой подписок. Если есть другие внешние способы входа, автоматическое слияние запрещено.
- Совпадение имени/email/телефона VK **не является основанием для объединения**. Нужно явно доказать оба аккаунта. Существующие Telegram, Яндекс и email входы сохраняются.

## Порядок активации

1. Создать Web-приложение VK ID в кабинете разработчика. Зарегистрировать точный redirect:
   `https://servgo.ru/api/auth/vk/callback`.
2. На сервере **основного ServGo API** настроить:
   ```env
   SERVGO_VK_ID_APP_ID=<APP_ID>
   SERVGO_VK_ID_REDIRECT_URI=https://servgo.ru/api/auth/vk/callback
   ```
   `JWT_SECRET` и `STUDIO_SSO_SECRET` должны сохранять прежние значения. Секреты не включать в Git.
3. Применить `migrations/add_vk_login.sql` к PostgreSQL базы BookingBot с резервной копией, не удаляя прежних таблиц.
4. Развернуть API и собранный фронтенд **одним согласованным выпуском**: новая кнопка не должна появляться до появления API. VK login откроется только при настроенном APP_ID.
5. В Codespace запустить:
   ```bash
   python -m pytest -q tests/test_vk_auth.py tests/test_yandex_auth.py tests/test_studio_sso.py
   cd web/frontend && npm ci --legacy-peer-deps && npm run build
   ```
   В PR в существующий PWA CI добавлены VK регрессионные тесты; не нужны отдельные GitHub Actions.
6. В тестовом браузере проверить вход VK и редирект в Studio; затем из уже существующего аккаунта через Telegram или Яндекс проверить «Профиль → Привязать VK» и что список организаций **не меняется**. Для ранее созданного VK-only аккаунта — подтверждение слияния, без потерянных организаций и подписок.
7. Проверить отрицательные случаи: отмена доступа, истёкший/неверный `state`, чужой браузер, повтор билета, VK уже привязан к другому полноценному аккаунту, попытка объединения двух оплаченных подписок.

## Технический контракт

- OAuth 2.1 `authorization_code` + PKCE `s256`, state-проверка в короткоживущем подписанном HttpOnly cookie.
- Сервер: `https://id.vk.ru/oauth2/auth` с `device_id`, затем `https://id.vk.ru/oauth2/user_info`. Запросы идут только по фиксированным адресам с `trust_env=False`, без follow redirects. Вход по стабильному `user_id`.
- В БД хранятся только соответствие `vk_user_id → users.id` и одноразовые браузерные билеты. **VK access token и refresh token для входа не сохраняются.**
- Callback создаёт случайный билет и передаёт его браузеру во фрагменте URL, связывает с HttpOnly cookie. Запрос `/api/auth/vk/exchange` одноразовый, токен пользователя ServGo выдаётся после транзакционной проверки. Legacy user IDs/связи остаются.
- Новая учётная запись без известных привязок имеет роль клиента. Роль владельца бизнеса определяется **по существующей БД** после привязки/входа.
- Это вход **пользователя**, а не VK API `wall.post`. Для публикаций нужен отдельный разрешённый ключ сообщества/подтверждённый OAuth.
